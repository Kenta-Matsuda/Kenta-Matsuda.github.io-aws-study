# 効率化・自己拡張ログ

- 最終更新日: 2026-09-06
- 対象範囲: 作業の効率化・低コスト化（繰り返し作業のスクリプト化によるトークン削減）の検討ログと、自己拡張（プロンプト・skill の改善）提案ログ
- 出典/参照: issue #69 #184 / `.kiro/agents/exam-content-maintainer.md` / `.kiro/agents/github-issue-resolver.md` / `scripts/issue-triage.mjs` / `scripts/check-resource-links.mjs` / `scripts/list-aws-doc-pages.mjs` / `scripts/list-action-required.mjs`

> エージェントが実行のたびに自分の作業を振り返り、**トークン消費と手間を減らす**アイデアと、**自分自身の能力を拡張する**提案を記録するログです。スキーマ（メタデータ + 更新履歴）は [README](README.md) を参照してください。

## ツールキット（実装済み / まずこれを使う）

棚卸し（リソース / issue のいずれも）を始めるときは、LLM が生データを 1 件ずつ読む前に**必ず次のスクリプトを実行**し、要約だけを読み込んでください。

| スクリプト | 役割 | 代表的な実行例 |
| --- | --- | --- |
| `scripts/issue-triage.mjs` | open issue + 関連 PR の 3 種コメントを取得し、`PR_FOLLOWUP` / `RECHECK` / `TRIAGE` / `OPEN_PR` / `SKIP` の判定つき要約を出力（読み取り専用） | `node scripts/issue-triage.mjs` / `node scripts/issue-triage.mjs --issue 138,32` |
| `scripts/check-resource-links.mjs` | `js/data/` 全試験から `url` / `urlEn` を抽出し、HTTP 死活・リダイレクト・ソフト 404・テキストフラグメントの陳腐化を分類して一覧化 | `node scripts/check-resource-links.mjs --concurrency 10 --fragments --json test-results/links-all.json` |
| `scripts/list-aws-doc-pages.mjs` | AWS 公式ドキュメント 1 ページから同一ガイド内の下位ページ / ページ内アンカーを抽出 | `node scripts/list-aws-doc-pages.mjs <url> --titles` / `... --anchors` |
| `scripts/analyze-resource-coverage.mjs` | 試験ガイドのタスクステートメント単位で items 件数・リソース種別を集計し、0 件 / 薄い / 単一種別のタスクを順位付け（ネットワーク不要） | `node scripts/analyze-resource-coverage.mjs --md test-results/coverage.md` |
| `scripts/list-action-required.mjs` | `docs/action-required/` の各ファイルのステータス行から要人間対応チェックリストを生成（読み取り専用。`--write` で `CHECKLIST.md` 再生成、`--check` で最新性検証） | `node scripts/list-action-required.mjs --write` / `node scripts/list-action-required.mjs --check` |

`check-resource-links.mjs` は差し替え候補の当たり付けにも使えます（`--urls "https://a,https://b" --all`）。候補を推測で書き込む前に、必ずこのモードで実在とリダイレクト先を確認してください。

## 記録の目的

- 「LLM が毎回自然言語で処理していた定型作業」を「スクリプト + 結果の要約読み込み」に置き換え、**コンテキスト投入トークンを削減**する。
- 効率化・自己拡張の**検討結果と効果（見込み / 実測）**を残し、次回以降の自分が参照できるようにする。
- 自己改変（プロンプト / skill / スクリプト）は必ず **PR ベース・人間レビュー前提**で提案する。

## 効率化アイデアのエントリ（実績）

### 2026-09-06: URL 棚卸しの集計を `scripts/collect-resource-urls.mjs` に切り出し（実装済み）

- **日付**: 2026-09-06
- **対象作業**: 「サイトが扱うユニークな AWS ドキュメント数」の算出。従来は `js/data/*.js`（13 試験 + 共通定義）を LLM が読み込んで数える必要があった。
- **課題**: 対象ファイルの総量が大きく、URL 参照は 1,771 件ある。LLM に全文投入すると数十万トークン規模になり、しかも数え間違いが起きる。
- **実装**: `scripts/collect-resource-urls.mjs` を追加。`js/data/` の各モジュールを動的 import し、`url` / `urlEn` を再帰抽出して次を出力する。
  - リソース項目数（`resources[].items[]`）、URL 参照数、ユニーク URL 数、ユニーク文書数（ja/en 統合）、ユニークページ数（フラグメント除去）、AWS 公式ドメイン比率、試験別内訳、ドメイン別内訳。
  - `--json <path>` で全ユニーク URL 付きの JSON を出力（後続のリンク死活チェッカの入力に流用可能）。`--list` で URL 一覧のみ出力。
- **設計上の判断**:
  - ja/en の統合は `/jp`・`/ja_jp` のロケールパス除去で行う。**テキストフラグメント（`#:~:text=`）は保持**する。Black Belt 一覧ページ（`aws.amazon.com/jp/blogs/news/aws-blackbelt-overview/`）は 1 ページ内の個別資料をフラグメントで指しており、除去すると 130 本以上の資料が 1 件に潰れて実態を大きく下回るため。フラグメント除去版も別指標（ユニークページ）として併記する。
  - AWS 公式判定は `aws.amazon.com` / `amazonaws.com` / `awsstatic.com` / `awscloud.com` / `aws.training` / `*.aws`（skillbuilder・repost・calculator）/ `wellarchitectedlabs.com` を対象にする。
- **実測効果**: 集計 1 回あたり、データファイル全文投入（概算 30 万トークン超）→ スクリプト出力サマリ約 40 行（約 1.5 千トークン）に置き換え。**99% 以上の削減**。棚卸しのたびに再利用でき、数値の再現性も担保される。
- **状態**: 実装済み（本 PR）。実測値は `docs/wiki/exam-resource-inventory.md` の「リソース規模（統計）」に記録。
- **次の一手**: 同じ抽出ロジックを流用して HTTP ステータス確認までを行うリンクチェッカ（ネットワーク可能環境で実行）を追加する。`--json` 出力をそのまま入力にできる形にしてある。

## 効率化ログ（実績）

### 2026-09-06: リンク死活チェックのスクリプト化（実装済み）

- **日付**: 2026-09-06
- **対象作業**: `js/data/*.js` の全 `url` / `urlEn` を LLM が抽出し 1 件ずつ確認していた作業。
- **課題**: 対象は 14 ファイル・**`url`/`urlEn` フィールド 1,771 件 / ユニーク URL 1,092 件**（実測）。自然言語で抽出・確認すると投入トークンが極端に大きく、再現性も低い。
- **実装**: `scripts/check-resource-links.mjs`。データファイルを動的 `import` して**深さ優先で `url`/`urlEn` を持つオブジェクトを収集**するため、スキーマが多少変わっても壊れない。HTTP は HEAD → GET フォールバックで確認し、結果を `broken` / `soft-404` / `error` / `server-error` / `fragment-miss` / `redirect` / `forbidden` / `locale-redirect` / `ok` に分類する。
- **実測効果**:
  - **リクエスト数削減**: フラグメント（`#...`）は HTTP では送られないため、フェッチを**フラグメント除去後の URL 単位**で重複排除。ユニーク URL 1,092 件 → 実 HTTP リクエスト **911 件**（Black Belt 一覧ページへのテキストフラグメント付きリンクが多いため）。フラグメント本文検証が必要なページはさらに **4 ページ**に収束した。
  - **投入トークン削減**: LLM が読むのは 1,092 行超の URL 一覧ではなく**問題行のみの要約**。初回実行の要約は `broken` 15 / `soft-404` 24 / `fragment-miss` 19 / `redirect` 67 / `forbidden` 4 の計 **129 件**まで絞られた（`ok` 757 件と `locale-redirect` 206 件は既定で出力しない）。読み込み量として概ね **1/8 以下**。
  - **判断品質の向上**: 分類を分けたことで「本当に直すべきもの」と「ノイズ」が分離された（下記の 2 つの落とし穴を参照）。
- **状態**: 実装済み。静的検証は `node --check scripts/check-resource-links.mjs` を通過。

### 2026-09-06: ガイド内ページ / アンカー列挙のスクリプト化（実装済み）

- **日付**: 2026-09-06
- **対象作業**: 「このガイドにもっと適切な章はないか」を LLM が推測し、候補 URL を当て推量で HTTP 確認していた作業。
- **実装**: `scripts/list-aws-doc-pages.mjs`。指定ページから同一ガイド配下の下位ページ（`--titles`）またはページ内見出しアンカー（`--anchors`）を抽出する。
- **実測効果**: 推測による候補生成と往復が不要になった。実例:
  - AIB-C01 試験ガイドに**ドメイン別ページと「スコープ内 / スコープ外サービス」ページが実在**することを 1 回の実行で確定（8 ページ）。
  - AWS CAF for AI ホワイトペーパーは**単一ページ構成**（下位ページは改訂履歴のみ、ページ内アンカーも 4 個）であることを確定。同一 URL を複数タスクで使い回すのは仕様上避けられないと結論でき、無駄な差し替え検討を打ち切れた。
  - SageMaker Clarify の後継ページ名（`clarify-configure-processing-jobs.html` = "Fairness, model explainability and bias detection"）を、推測ではなく目次から特定できた。
- **状態**: 実装済み。静的検証は `node --check scripts/list-aws-doc-pages.mjs` を通過。

### 2026-09-06: タスクステートメント単位のカバレッジ分析のスクリプト化（実装済み）

- **日付**: 2026-09-06
- **対象作業**: 「どの試験のどのタスクがリソース不足か」の判断。従来は `js/data/*.js`（13 ファイル・計 1 万行超）を LLM が読んで感覚的に判断するしかなかった。
- **課題**: 全ファイルを読むと数十万トークン規模。かつ「薄い」の基準が実行ごとにぶれ、優先順位が再現しない。
- **実装**: `scripts/analyze-resource-coverage.mjs`。`domains[].tasks[]` ごとに items 件数・リソース種別（doc / blackbelt / blog / training / whitepaper / architecture / repost / whats-new / product / lab / builders-library）・`knowledge` 件数を集計し、次を出力する。
  - 試験別サマリ（タスク数 / items 合計 / 中央値 / 最小 / 最大 / 0 件 / 薄い / 単一種別）
  - items が少ない順の補強優先タスク一覧
  - `--md` / `--json` でのファイル書き出し（PowerShell 環境の文字化けを回避できる）
- **設計上の判断**:
  - **HTTP アクセスは行わない**（静的解析のみ）。`check-resource-links.mjs` が担う死活チェックとは目的が異なり、こちらは「量と多角性の不足」を見る。オフライン環境でも常に実行できる。
  - `steps[]`（申し込み・試験ガイド等の共通導線）は対象外とし、**試験ガイドのタスクステートメントに 1:1 対応する `domains[].tasks[]` のみ**を評価する。カバレッジの議論はタスク単位でしか意味を持たないため。
  - リソース種別を分類したのは、「件数は足りているが `docs.aws.amazon.com` だけ」という**多角性の不足**を検出したかったため。実測で単一種別のタスクが 15 件見つかった。
- **実測効果**: データファイル全文投入（概算 30 万トークン超）→ 出力サマリ 20 行 + 上位タスク表（約 2 千トークン）。**99% 以上の削減**。加えて、優先順位が数値で固定されるため実行間で判断がぶれない。
- **実測結果（2026-09-06 / 全 13 試験・206 タスク・items 979）**: 0 件タスク無し。薄い（3 件未満）16 / 単一種別 15。中央値は ANS-C01 が 8 で最高、AIB-C01 が 2 で最低。詳細は `docs/wiki/exam-resource-inventory.md` の「カバレッジ台帳」。
- **状態**: 実装済み。静的検証は `node --check scripts/analyze-resource-coverage.mjs` を通過。

### 2026-09-06: 試験ガイド文言ドリブンの探索方針（1 件以上を必ず確保する）をプロンプトへ制度化

- **日付**: 2026-09-06
- **対象**: `.kiro/agents/exam-content-maintainer.md`（本エージェントのプロンプト）/ `docs/wiki/aws-resource-discovery.md`。
- **背景（リポジトリオーナーの指摘）**: ANS-C01 のリソースが多いのは**手作業で試験ガイドの文言を一つ一つチェックし、関連ドキュメントを片っ端から調べた**ため。この方針をエージェントの標準手順にしたい。特に「AWS ドキュメントに良いものが無い」で諦めず、多角的に調べて**必ず 1 件以上を確保する**方向にしたい。
- **提案内容**:
  1. `docs/wiki/aws-resource-discovery.md` に「試験ガイド文言ドリブンの探索手順」節を新設。タスクステートメントと `knowledge` 箇条書きを 1 行ずつ分解して**語の数だけ検索軸を作る**手順、9 段のフォールバック順序（ドキュメント → Black Belt → 公式ブログ → Skill Builder → ホワイトペーパー / Well-Architected → WA Labs / Builders' Library → re:Post KC → What's New / FAQ / 料金 → プロダクトページ）、カバレッジ目標（1 件以上必須 / 原則 3 件以上 / 2 種別以上）を明文化。
  2. プロンプトに「主要機能 1b: カバレッジ拡充」を新設し、棚卸し（既存リンクの鮮度維持）と対をなす柱として位置付け。着手前後の `analyze-resource-coverage.mjs` 実行と before / after の PR 記載を義務化。
  3. 禁止事項に **「良いドキュメントが無いことを理由にタスクを 0 件で終わらせない」** と **「削除だけで棚卸しを終えない（削除でカバレッジが落ちたら代替を探す）」** を追加。
- **理由・期待効果**: 従来のプロンプトは「リンク切れの差し替え・削除」に強く寄っていて、**削除でカバレッジが下がる方向のバイアス**があった。実際、直近の棚卸し PR 群はリンク修正・削除が中心だった。拡充を明示的な主要機能に格上げし、数値目標とスクリプトによる測定を紐付けることで、リンクが健全なだけでなく**学習リソースとして厚い**状態へ進む。
- **想定リスク**: 権限緩和は無し（禁止事項の追加のみ）。件数目標を機械的に追うと質の低いリンクを埋める誘惑が生じるため、「候補 URL は実アクセス検証してから書き込む」「プロダクトページのみは掘り足りないサイン」という既存の質のガードを明記して併走させた。
- **状態**: 実装済み（本 PR）。

### 2026-09-06: 実行環境を断定しない前提への修正と、ツールキット優先の手順化

- **日付**: 2026-09-06
- **対象**: `.kiro/agents/exam-content-maintainer.md`（本エージェントのプロンプト）
- **提案内容**:
  1. **「サンドボックス実行環境の事実」を「実行環境の事実」に改題し、環境を断定しない前提に改めた。** 従来は「OS は Linux、シェルは bash」「INTEGRATIONS_ONLY 環境では外部アクセス不可」と断定していたが、実測で **Windows / PowerShell 7 かつネットワーク利用可能**な環境でも起動されることが判明した。
  2. **「手順 0: 着手時の環境判定」を新設**し、OS / シェル・`NODE_OPTIONS`・ネットワーク可否の 3 点を最初に確認することを必須化。判定結果を最終報告に明記させる。
  3. **PowerShell 環境固有の落とし穴を明文化**: ヒアドキュメント不可（コミットメッセージ / PR 本文はファイル経由で渡す）、`env -u NODE_OPTIONS` 不可（`$env:NODE_OPTIONS=''` を使う）、コンソール出力の日本語が CP932 で文字化けする（git 内部は正しい UTF-8 なので誤認しない / 長い出力はスクリプトから UTF-8 ファイルへ直接書き出す）。
  4. **「ツールキット」節を新設**し、`scripts/check-resource-links.mjs` / `scripts/list-aws-doc-pages.mjs` を棚卸しの第一手として使うこと、**候補 URL を推測で書き込まないこと**を手順・禁止事項の両方に明記。
  5. **「HTTP ステータスだけでは判定できない落とし穴」を要約して掲載**（ロケールリダイレクト / ソフト 404 / フラグメント陳腐化 / SPA ドメイン / 新規顧客の受付終了）。
  6. **検証節を具体化**: `js/data/` の URL を変更したら `--only <試験コード>` で 0 件を確認し、修正前後の件数を PR 本文に載せることを必須化。あわせて「URL / タイトル / 注記 / `recommend` のみの変更なら Playwright を省略してよい（ただし理由を PR に明記）」という判断基準を追加。
  7. **一時的な調査用スクリプトは gitignored な `test-results/tools/` に置く**ルールを追加（リポジトリを汚さない / 再利用価値が出たら `scripts/` へ昇格させて PR で提案）。
  8. ラベルが未定義のリポジトリでは先に作成が必要なこと、`gh api --jq` の式は PowerShell ではシングルクォートで囲むことを追記。
- **理由・期待効果**: 環境を断定していたため、Windows / PowerShell 環境では**プロンプト記載のコマンド（`env -u NODE_OPTIONS`、ヒアドキュメント）がそのままでは失敗**する。またネットワーク不可を前提としていたため、実際には可能な実地検証を「できない」と誤判断して手順整備だけで終える危険があった。環境判定を先頭に置き、ツールキットを第一手として固定することで、次回以降は同じ試行錯誤を繰り返さずに本題（リソースの是正）へ直行できる。
- **想定リスク**: 権限緩和・既存制約の削除は無し。既存の禁止事項はすべて維持し、制約の追加・具体化のみ。唯一の緩和方向の変更は「URL のみの変更なら Playwright 省略可」だが、**理由の明記を条件**にしており、従来の「実行できなければ理由を記録」運用の範囲内。

### 2026-09-06: 既存オープン PR のコンフリクト解消を能動的な必須手順として制度化

- **日付**: 2026-09-06
- **対象**: `.kiro/agents/github-issue-resolver.md`（プロンプト） / `docs/wiki/issue-resolution-playbook.md`（落とし穴 A-7・コマンド追加） / 本ログ。

- **実施した仕組み変更**:
  1. **新設「既存オープン PR のコンフリクト解消（コメントが無くても能動的に解消する）」節**（主要機能 1 内）。`gh api repos/{owner}/{repo}/pulls/{n} --jq '{mergeable, mergeable_state, rebaseable}'` を**PR 単体で**叩いて判定し、`dirty` / `behind` を依頼の有無に関係なく解消対象とする。`unknown` は GitHub の計算中（`mergeable` が `null`）なので数秒待って再取得し、それでも不明なら `git rev-list` にフォールバックする。実施タイミングは**新規 issue の実装より先**（マージできない PR を増やさない）。
  2. **解消手段を `git merge origin/main` に固定**。`git rebase`・force push・PR クローズして作り直す回避を明確に禁止し、`permissions.rules` の deny に `git rebase*` を追加した。
  3. **解消品質の具体則を明文化**: `--ours` / `--theirs` の一括適用禁止、双方の意図を保持（捨てる場合は理由を PR コメントに明記）、`js/locales/*.json` はパース + ja/en キー相互ミラー確認、`js/data/*.js` は双方の追加項目を取りこぼさない、解消不能なら `git merge --abort` して PR コメントで状況を説明（黙って放置しない）。
  4. **解消後の検証と締めを手順化**: `git diff origin/main...HEAD --stat` で PR 本来の変更が消えていないことを確認、静的検証を実施、push 後に `mergeable_state` の解消を再確認、`🤖 対応済み` 接頭辞で要約コメントを残す。
  5. **参照される位置への配置**: 手順 1 のコメントファースト事前ゲートに **(iii) マージ可能状態の確認**を追加し、「コンフリクトしていることはスキップ理由にならない」と明記。#141 チェックリストの (c) を behind main 限定から**マージ可能状態全般**へ拡張。報告項目にも解消結果（解消前後の `mergeable_state` / 対象ファイル / 解消方針 / 検証）を追加した。
  6. **playbook に落とし穴 A-7 として記録**し、`mergeable_state` の各値の扱いと `git` フォールバックを「再利用可能なコマンド」節へ追加した。
- **教訓（一般化）**: 「依頼されたら対応する」形の受動的ルールは、依頼が来ない限り実行されない。**状態を自分から観測する手順（どの API のどのフィールドを見るか）**まで書いて初めて能動的な運用になる。あわせて、一覧 API と単体 API で返るフィールドが異なる点は明記しておかないと恒久的に見落とされる。
