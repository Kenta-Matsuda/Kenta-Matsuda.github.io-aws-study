# 効率化・自己拡張ログ

- 最終更新日: 2026-09-06
- 対象範囲: 作業の効率化・低コスト化（繰り返し作業のスクリプト化によるトークン削減）の検討ログと、自己拡張（プロンプト・skill の改善）提案ログ
- 出典/参照: issue #69 / `.kiro/agents/exam-content-maintainer.md` / `.kiro/agents/github-issue-resolver.md`

> エージェントが実行のたびに自分の作業を振り返り、**トークン消費と手間を減らす**アイデアと、**自分自身の能力を拡張する**提案を記録するログです。スキーマ（メタデータ + 更新履歴）は [README](README.md) を参照してください。

## 記録の目的

- 「LLM が毎回自然言語で処理していた定型作業」を「スクリプト + 結果の要約読み込み」に置き換え、**コンテキスト投入トークンを削減**する。
- 効率化・自己拡張の**検討結果と効果（見込み / 実測）**を残し、次回以降の自分が参照できるようにする。
- 自己改変（プロンプト / skill / スクリプト）は必ず **PR ベース・人間レビュー前提**で提案する。

## 効率化アイデアのエントリ形式（例）

各エントリは次の項目で記録します。以下は**記入例（サンプル）**であり、実測値ではありません。

### 例: リンク死活チェックのスクリプト化

- **日付**: 2026-09-03（例）
- **対象作業**: `js/data/*.js` の全 `url` / `urlEn` を LLM が手作業で抽出し 1 件ずつ確認していた。
- **課題**: URL 抽出と確認を自然言語で毎回行うとトークン消費が大きく、再現性も低い。
- **アイデア**: `scripts/` に「全試験ファイルから `url`/`urlEn` を抽出し HTTP ステータスを一覧化する」リンクチェッカを実装し、LLM は**結果サマリだけ**を読み込む。
- **想定効果（見込み）**: URL 一覧の生投入が不要になり、確認 1 巡あたりの投入トークンを削減。
- **状態**: アイデア（未実装）。実装時は `env -u NODE_OPTIONS node --check` で静的検証し、PR で提案する。

## 効率化アイデアのエントリ（実績）

### 2026-09-06: URL 棚卸しの集計を `scripts/collect-resource-urls.mjs` に切り出し（実装済み）

- **日付**: 2026-09-06
- **対象作業**: 「サイトが扱うユニークな AWS ドキュメント数」の算出。従来は `js/data/*.js`（13 試験 + 共通定義）を LLM が読み込んで数える必要があった。
- **課題**: 対象ファイルの総量が大きく、URL 参照は 1,771 件ある。LLM に全文投入すると数十万トークン規模になり、しかも数え間違いが起きる。
- **実装**: `scripts/collect-resource-urls.mjs` を追加。`js/data/` の各モジュールを動的 import し、`url` / `urlEn` を再帰抽出して次を出力する。
  - リソース項目数（`resources[].items[]`）、URL 参照数、ユニーク URL 数、ユニーク文書数（ja/en 統合）、ユニークページ数（フラグメント除去）、AWS 公式ドメイン比率、試験別内訳、ドメイン別内訳。
  - `--json <path>` で全ユニーク URL 付きの JSON を出力（後続のリンク死活チェッカの入力に流用可能）。`--list` で URL 一覧のみ出力。
- **設計上の判断**:
  - ja/en の統合は `/jp`・`/ja_jp` のロケールパス除去で行う。**テキストフラグメント（`#:~:text=`）は保持**する。Black Belt 一覧ページ（`aws.amazon.com/jp/blogs/news/aws-blackbelt-overview/`）は 1 ページ内の個別資料をフラグメントで指しており、除去すると 130 本以上の資料が 1 件に潰れて実態を大きく下回るため。フラグメント除去版も別指標（ユニークページ）として併記する。
  - AWS 公式判定は `aws.amazon.com` / `amazonaws.com` / `awsstatic.com` / `awscloud.com` / `aws.training` / `*.aws`（skillbuilder・repost・calculator）/ `wellarchitectedlabs.com` を対象にする。
- **実測効果**: 集計 1 回あたり、データファイル全文投入（概算 30 万トークン超）→ スクリプト出力サマリ約 40 行（約 1.5 千トークン）に置き換え。**99% 以上の削減**。棚卸しのたびに再利用でき、数値の再現性も担保される。
- **状態**: 実装済み（本 PR）。実測値は `docs/wiki/exam-resource-inventory.md` の「リソース規模（統計）」に記録。
- **次の一手**: 同じ抽出ロジックを流用して HTTP ステータス確認までを行うリンクチェッカ（ネットワーク可能環境で実行）を追加する。`--json` 出力をそのまま入力にできる形にしてある。

## 自己拡張（プロンプト・能力）提案のエントリ形式（例）

- **日付**: YYYY-MM-DD
- **対象**: `.kiro/agents/exam-content-maintainer.md`（本エージェントのプロンプト） / `.kiro/` 配下の skill など。
- **提案内容**: 追記・改善する手順 / 判断基準 / 禁止事項の具体。
- **理由・期待効果**: なぜ必要か、何が改善されるか。
- **想定リスク**: 権限緩和の有無など（権限緩和は特に慎重に、理由を明記して PR レビューを仰ぐ）。
- **状態**: 提案 / 実装済み（PR 番号）など。

## 自己拡張提案ログ（実績）

### 2026-09-05: コメントファースト前提条件の明文化とレトロスペクティブ/自己改善ループの制度化

- **日付**: 2026-09-05
- **対象**: `.kiro/agents/github-issue-resolver.md`（issue-resolver エージェントのプロンプト） / 本ログ `docs/wiki/efficiency-log.md`。
- **提案内容**:
  1. コメントファーストのハード前提条件を `手順` の先頭（新・手順 1）へ移設。どの issue でも、着手・見送り（スキップ）判断の前に、issue 自身のコメントと、関連するすべての PR（open / closed / merged）のコメント 3 種（ディスカッション `/issues/{n}/comments`、インライン `/pulls/{n}/comments`、レビュー `/pulls/{n}/reviews`）を必ず読むことを無条件で要求。「オープン PR がある」ことは、それ単独ではスキップ理由にならないと明記。
  2. 「振り返り（レトロスペクティブ）と自己改善ループ（必須）」節を新設。バッチ着手時に「なぜこれまで対応されずに残っていたのか」を自省して根本原因を特定し、プロセス改善を恒久ルール（本マニュアル / `docs/`）へ書き戻して独立した `chore:` 仕組み変更 PR として発行することを義務化。振り返りは本ログに日付付きで記録し、最終報告にも要約と仕組み変更 PR を含めることを必須化。
- **理由・期待効果**: コメントファーストの指針は既に「既存オープン PR の新規コメント対応」節に存在したが、埋もれていて参照されず遵守されなかった。その結果、オープン PR（PR #114 / issue #32、PR #113 / issue #109）に付いていたユーザーのエスカレーション済みコメントが未対応のまま放置された。前提条件を先頭へ移し、かつ自省→仕組み反映のループを制度化することで、同種の見落としを恒久的に防ぎ、改善が積み重なって加速する。
- **想定リスク**: 権限緩和・既存制約の削除は無し（既存の禁止事項はすべて維持し、制約の追加・明確化・再配置による強化のみ）。
- **状態**: 実装済み（本 PR）。
