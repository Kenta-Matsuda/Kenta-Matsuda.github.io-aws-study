# AI検索をHyDEでクエリ拡張し、検索導線を強化 (#201)

## 背景（何が問題だったか）

横断リソース検索（#189 で追加）には「キーワード検索」と「AI検索」の 2 つのボタンがある。
しかし AI検索は、**まずユーザーのクエリでキーワード検索を実行し、そのヒットだけを AI に
再ランクさせる**実装だった。

このため「分析用のAIサービス」のような**ふわっとした自然言語のクエリ**は、どのリソースの
検索対象文字列（title / note / url / group ラベルを日英まとめた haystack）にも部分一致
せず、候補が 0 件になる。候補が 0 件だと AI は呼ばれず、AI検索なのに「一致するリソースが
ありません」で終わってしまい、**通常のキーワード検索と実質同じ**挙動になっていた。

issue では、ユーザーがこの状態を **HyDE（Hypothetical Document Embeddings）** と名指しで
提案している。「キーワードでは『Amazon Quick』のように具体語で検索するが、AI検索では
『分析用のAIサービス』のような曖昧な状態から検索できるようにしたい」という要望である。

あわせて、「検索機能が右上の虫眼鏡ボタンだけだと導線が弱い。検索用の（トップページ的な）
入口を用意すべき」という指摘もある。

## 実装方針

### 1. HyDE によるクエリ拡張

AI検索ボタンの処理を次の流れに変更した（`js/ui.js` の `wireResourceSearchHandlers`）。

1. **クエリ拡張（HyDE）**: ユーザーの（曖昧な）クエリを AI に渡し、「このクエリに答える
   AWS 認定の学習トピックを想像し、その文書に現れる具体的な AWS サービス名 / キーワードを
   出力させる」。出力は「Amazon SageMaker, Amazon Bedrock, Amazon Comprehend」のような
   カンマ区切りのキーワード列のみを求める（URL や文章は求めない）。
2. **ローカル索引の和集合検索**: 生成された展開語のそれぞれで `searchResources` を実行し、
   結果を (examId + url) をキーに **和集合（union）+ 重複排除（dedupe）** する。元のクエリ
   自体も 1 つの語として含めるので、既に一致していたクエリの挙動は退行しない。
3. **AI による厳格なランク付け**: 得られた候補リストを従来どおり AI に渡し、「候補リストの
   中からのみ推薦・ランク付けする（URL やタイトルを捏造しない）」grounding で回答させる。

拡張が何も返さない / AI 呼び出しが失敗した場合は、元クエリの素のキーワード検索に
フォールバックする。

### 2. テスト可能なピュアヘルパーへの切り出し

和集合 + 重複排除のロジックは、`js/resourceSearch.js` に **エクスポートされたピュア関数**
`searchResourcesMulti(index, terms, { examId, perTermLimit, limit })` として実装した。
DOM / ネットワーク非依存なのでブラウザ無しで単体テストできる。AI 呼び出し自体
（曖昧なクエリ → 展開語）は UI 層（`js/ui.js`）に残し、`callAi` を用いて実行する。

回帰テストは `tests/ai-search-hyde.spec.mjs`。「元の曖昧なクエリでは 0 件だが、展開語の
和集合では候補が得られる」「複数の展開語が当たったレコードは 1 件に重複排除される」
「recommend:true が先頭に来る」ことなどを検証する。

### 3. API キー未設定時のフォールバック

キー未設定時は、**設定モーダルを検索モーダルの上に開かず**、素のキーワード検索の結果を
表示したうえで、既存のローカライズ済み通知（`search.aiNeedsKey`）を出す。これは #189 で
定めた既存挙動を踏襲している。

### 4. 検索導線の強化

右上の虫眼鏡ボタンだけでなく、**ダッシュボードの学習ステータスパネル**（トップ表示領域）に
検索ボックス風のラベル付きボタン（`#dashboardSearchBtn`）を追加した。押すと**既存の**横断
検索モーダルを開く（虫眼鏡ボタンと同じ配線を再利用）。新しいページ / ルーターは作らない。
表示文字列は `data-i18n="dashboard.searchCta"` で ja / en 両方にミラーキーを追加した。

## 変更ファイル

- `js/resourceSearch.js`: ピュア関数 `searchResourcesMulti` を追加。
- `js/ui.js`: HyDE 拡張（`expandQueryToAwsKeywords` / `parseExpandedKeywords`）、AI検索
  ハンドラの流れ変更、ダッシュボード検索ボタンの配線。
- `index.html`: ダッシュボードに検索導線ボタンを追加。
- `js/locales/ja.json` / `js/locales/en.json`: `dashboard.searchCta` を相互ミラーで追加。
- `tests/ai-search-hyde.spec.mjs`: 和集合 / 重複排除の回帰テスト（新規）。
- `docs/issues/ai-search-hyde-201.md`（本ファイル） / `docs/index.md`。

## 考慮したトレードオフ

- **AI 呼び出しが 1 回増える**: 拡張のための呼び出しと、ランク付けのための呼び出しの 2 回に
  なる。レイテンシとコストは増えるが、いずれもユーザー自身の API キーで動くクライアント
  サイド処理であり、既存のバックエンドレス設計を崩さない。拡張出力は 8 語程度に制限して
  プロンプトサイズを抑えている。
- **拡張の品質はモデル依存**: 生成キーワードが的外れだと候補が弱くなる。ただし元クエリも
  必ず語に含め、拡張が空 / 失敗ならキーワード検索にフォールバックするので、少なくとも従来と
  同等の結果は保証される。
- **導線は最小変更にとどめた**: 「トップページ」を新設せず、既存のダッシュボード上に検索
  入口を足す形にした。専用ページ / ルーターの新設は影響範囲が大きいため見送った。

## 検証

このサンドボックスは Playwright を実行できない（INTEGRATIONS_ONLY / npm レジストリが 403 /
ブラウザ未キャッシュ）。そのため静的検証と、ピュアヘルパーの直接実行で確認した。

- `env -u NODE_OPTIONS node --check` を `js/ui.js` / `js/resourceSearch.js` /
  `tests/ai-search-hyde.spec.mjs` に対して実行 → OK。
- `js/locales/ja.json` / `en.json` を `JSON.parse` → OK。ja / en のキー集合が相互ミラーで
  あることを確認 → OK。
- `searchResourcesMulti` を `node` で直接実行し、「分析用のAIサービス」の素の検索は 0 件、
  展開語（Amazon SageMaker / Bedrock / Comprehend）の和集合では候補が得られること、
  重複排除が効くことを確認。

### 手動再現手順

1. `env -u NODE_OPTIONS node dev-server.mjs` でローカルサーバを起動する。
2. ブラウザで開き、設定から Gemini か OpenAI の API キーを登録する。
3. ダッシュボードの検索導線ボタン（または右上の虫眼鏡）で横断検索モーダルを開く。
4. 「分析用のAIサービス」のような曖昧なクエリを入力し、「AI検索」を押す。
5. 展開語で見つかったリソース候補が一覧表示され、AI の推薦が候補リストの中から返ること、
   API キー未設定時はキーワード検索結果＋「AI検索にはAPIキーが必要」通知になることを確認する。
