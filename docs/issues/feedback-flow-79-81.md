# Issue: フィードバック送信フローの改善 (#79 / #81)

## 概要

フィードバック機能に関する2つの密接に関連するissueに対応する。

- **#79 [Feedback] General**: フィードバック送信時にGitHub issue作成画面が表示され、ユーザー自身がissueを作成する必要がある。ユーザーがGitHub issueを意識しなくてもよい設計にできないか。
- **#81 [Feedback] General**: フィードバックに画像を含められるようにしてほしい（画像添付）。

このサイトはビルドステップを持たない静的なクライアントサイドPWA（バニラJSのESモジュール）であり、GitHub Pagesで配信されている。バックエンドやオブジェクトストレージを持たないため、両issueを「完全に」満たすにはサーバー側の実装が必要になる（後述の「要人間対応」参照）。本対応では、バックエンドなしで実現できる範囲をクライアント側で最大限改善した。

## 変更内容（クライアント側で実装済み）

### 1. #79: GitHubへの受け渡しを自動的なステップに近づける
- `js/ui.js` の `submitFeedback` で、GitHub issueのプレフィル用URLを開く前に、組み立てたissue本文を既存の `copyTextToClipboard` ヘルパーで**自動的にクリップボードへコピー**するようにした。
- フィードバックモーダルの文言（`js/locales/ja.json` / `js/locales/en.json` の `feedbackModal.description` / `feedbackModal.sent`）を見直し、GitHubへの受け渡しが「自動的なステップ」として読めるように調整した（本文が自動コピーされ、プレフィル済みのissue画面が開く）。ただし送信が完全に自動化されたとは主張しない文言にとどめた。
- これにより、ユーザーの手作業は減るが、最終的なissue作成（送信ボタンの押下）は依然としてGitHub画面上で行う必要がある。GitHub画面を完全に不可視化するにはバックエンドが必要（後述）。

### 2. #81: 画像添付のアフォーダンスとGitHubへの貼り付け導線
- フィードバックモーダル（`index.html` の `#feedbackModal` と `js/ui.js`）に画像添付のUIを追加した。
  - 非表示のファイル入力（`accept=image/*`, `multiple`）
  - ドロップゾーン兼トリガーボタン
  - サムネイルプレビュー（`URL.createObjectURL` を使用し、リセット・クローズ時に `revokeObjectURL` で解放）
  - クリック / ペースト / ドラッグ&ドロップでの追加
  - サムネイルごとの個別削除
- GitHubのプレフィル済み新規issue URLはファイル添付を運べないため、**画像バイトはどこにもアップロードしない**。代わりに、開かれたGitHub issue画面へユーザーが画像を貼り付けるよう促すガイダンス／マーカーを本文に含めた（GitHubは貼り付けた画像を自動アップロードする）。
- 追加したロケールキー（`ja.json` / `en.json` の両方）: `imageLabel`, `imageAdd`, `imageHelp`, `imageRemove`, `issueImageMarker`, `sentWithImages`。

## 制約・残課題

上記のクライアント側改善で操作は大きく簡略化されるが、以下は静的サイトの制約上、本タスクの範囲では実現できない。

- **#79 の完全対応**: GitHub画面を一切表示せずにフィードバックを受け付けるには、送信を受けるバックエンドのエンドポイントが必要。
- **#81 の完全対応**: フォーム内で完結する画像アップロード（画像バイトの保存）には、サーバー側のオブジェクトストレージが必要。GitHubのトークンレスなプレフィルURLスキームはファイル添付を運べない。

これらはいずれもバックエンドとストレージを前提とするため、静的なGitHub Pagesサイト単体では実装できない。

## ⚠️ 要人間対応: AWS操作が必要

#79・#81 を「完全に」満たすには、フィードバックを受け取るバックエンドと画像バイトを保存するストレージが必要になる。これらの構築にはAWSリソースの作成・設定が伴うが、**本タスクの制約により AWS CLI（`aws ...`）などAWSリソースへの直接操作は一切実行していない**。以下は、人間が別途実施する必要がある作業の想定内容である。

### 想定される構成（例）
- **Amazon API Gateway**: フィードバック送信を受け付けるHTTP(S)エンドポイント。
- **AWS Lambda**: 受信したフィードバックを処理し、必要に応じてGitHub API等でissueを作成、または通知先へ転送する関数。
- **Amazon S3**: 添付画像のバイトを保存するオブジェクトストレージ（アップロード用の署名付きURL発行を含む）。
- （任意）**Amazon CloudFront** / **AWS WAF** / **Amazon DynamoDB**: 配信・保護・メタデータ保存が必要な場合。
- （任意）**AWS Secrets Manager** / **SSM Parameter Store**: GitHubトークン等の秘匿情報の保管。

### 人間が実施する必要がある操作の概形（実行はしていない）
1. S3バケットの作成と、画像アップロード用の署名付きURL発行ポリシー／CORS設定。
2. Lambda関数の作成・デプロイ（フィードバック受信・issue作成/転送・画像URLの紐付け）。
3. API GatewayのAPI作成、Lambda統合、CORS・スロットリング設定、ステージのデプロイ。
4. IAMロール／ポリシーの作成（Lambda→S3、Lambda→Secrets Manager等の最小権限付与）。
5. 秘匿情報（GitHubトークン等）のSecrets Manager／SSMへの登録。
6. フロントエンド（`js/ui.js` の `submitFeedback`）を、GitHubプレフィルURLではなく上記エンドポイントへ送信するよう差し替え。

> これらの `aws ...` コマンドやマネジメントコンソール操作は**実行していない**。実際の構築・権限付与・コスト発生を伴うため、担当者による確認・実行が必要（要人間対応）。秘匿情報はコミットに含めないこと。

## 検証について

- 本プロジェクトには**ビルドステップが存在しない**（バンドラ・トランスパイル無し。静的ファイルをそのまま配信）。`package.json` の `test` スクリプトはプレースホルダ。
- ブラウザベースのPlaywrightテストは、サンドボックスの **INTEGRATIONS_ONLY** ネットワーク制約により実行できなかった（npmレジストリへ到達できず `npm install` 不可、Playwrightのブラウザダウンロードも不可）。
- そのため検証は以下で代替した。
  - 変更したJSの構文チェック: `node --check js/ui.js`
  - ロケールファイルのJSONパース確認: `js/locales/ja.json` / `js/locales/en.json` を `JSON.parse` で検証
  - 変更したフィードバック処理パスの手動再読による論理確認
