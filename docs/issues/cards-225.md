# カード: 問題生成が参照する「何を問うか」をデータ化する (#225 / PR 5)

## 背景

設計書 [`../design/exam-generation-pipeline.md`](../design/exam-generation-pipeline.md) §4 の実装（段階導入計画の PR 5）。

多段パイプライン（PR 4）はタスクステートメントの箇条書きを出題単位にしていたが、技術系の試験ではもっと具体的（WAF の Bot 対策、TGW のマルチアカウント構成…）で、AWS Blogs の構築事例が最良の素材になる。一方 AIB のような抽象的な試験では CAF for AI などフレームワークの構造そのものを出題単位にすると、「正解はいつも CoE」のような収束が構造的に起きない。素材は実行時に読まず（ブラウザからは CORS で読めない）、**事前にカードとしてデータ化し、人間レビューを経てリポジトリに置く**。

## 実装したもの

### `js/cards.js`（新規・純ロジック）

- 3 種のカード: `case`（判断ポイント）/ `framework`（視点 × 段階 × 能力のセル）/ `concept`（用語）。
- `listUnits`: カードを出題単位（unit）へ平坦化。`validateCards`: スキーマ検証（出典 URL、不採用案の有無、タスク ID の実在、重複 ID）。`coverageReport`: 単位数 ≥ 問題数 × 1.5 かつ全タスクをカバーするか。`indexUnitsByTask` / `renderUnitForPrompt`（作問プロンプト用の素材描写。不採用案・誤解を**誤答の素材**として明示）。

### 最初のカード（人間レビュー前提）

- **`js/data/cards/aib-c01.js`** — フレームワーク・マップ。CAF for AI の 6 視点（Business / People / Governance / Platform / Security / Operations）の **AI 向けに拡張された能力**と変革の旅（4 要素・4 段階）を、能力ごとに 1〜3 セルに分解（約 60 セル）。各セルに要点・よくある誤解・対応タスク。段階（Envision / Align / Launch / Scale）は網羅のための編集上の対応付けで、ホワイトペーパー自身が能力を段階に割り当てているわけではない（ファイル冒頭に明記）。
  - **注意**: このホワイトペーパーは docs.aws.amazon.com で「historical reference only」（アーカイブ）表示になっている（2026-10-12 確認）。AIB の推奨リソースが参照している資料なので採用したが、`source.archived: true` として記録した。より新しい公式資料があれば差し替える判断は人間に委ねる。
- **`js/data/cards/saa-c03.js`** — ケースカード 4 枚（SCP のマルチアカウント運用、EDA の所有モデル、DR のパイロットライト／ウォームスタンバイ、S3 非カレントバージョンのコスト削減）、判断ポイント 17。いずれも SAA の推奨リソースにあるブログから抽出し、記事が触れていない点は推測せず「記事は言及していない」と記載。SCP 記事はクォータ更新の注記があるため `source.note` に明記。

### パイプラインへの組み込み

- `buildExamBlueprint` が `unitsByTask` を受け取り、**カードがあるタスクはカードの単位を、無いタスクはタスクステートメントの項目を**出題単位にする（部分的な在庫でも即座に効く）。計画プロンプトの行にカード由来であることを示し、作問プロンプトには `renderUnitForPrompt` の素材と「不採用案・誤解から誤答を作る」指示を付ける。
- `js/ui.js` は試験ごとに `js/data/cards/<exam>.js` を動的 import（無ければカード無し）。生成した問題の `unitId` にカード単位の ID を記録。

### 在庫検査と採掘モード

- `scripts/check-card-coverage.mjs`: 全試験の単位数／要件／未カバータスク／スキーマ問題を表示（`--strict` で CI 失敗）。
- `.kiro/agents/exam-content-maintainer.md` に「主要機能 1c: カード採掘」を追加（素材の選び方、出典とアーカイブ表示の記録、タスク対応付け、在庫検査、PR 単位）。
