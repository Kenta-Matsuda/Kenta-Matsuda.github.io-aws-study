# docs/action-required/ — 要人間対応事項の置き場

このディレクトリは、**まだ解決していない / 人間の対応が必要な事項**を構造化して残すための場所です。ここにあるファイルは「作業を止めた言い訳」ではなく、**引き継ぎ可能な成果物**として扱います。

`docs/issues/` が確定済み・対応済みの解説を置く場所であるのに対し、`docs/action-required/` は**未対応（要対応）**のものだけを置きます。対応が完了したら、このディレクトリからは削除し、必要に応じて `docs/issues/` などへ確定内容を移します。

## 命名と書式のルール

各ファイルは次のルールに従います。

- ファイル冒頭は必ずステータス行 **`🔴 未対応（要対応）`** で始める。
- ステータス行の近くに **種別**（例: AWS操作 / 外部サービス設定 / 手動確認）と **関連 issue / PR の参照**（`#<番号>`）を添える。
- 本文は次の見出しで構造化する:
  - **症状**: 観測されている問題・現象
  - **推定原因**: 現時点で考えられる原因
  - **切り分け手順**: 原因特定・確認のために踏むべき手順
  - **要人間対応事項**: 人間（またはAWS権限を持つ者）が行う必要がある作業
- AWS 操作が必要な場合は、要人間対応事項に次のブロックを必ず含める:

  ```
  ⚠️ 要人間対応: AWS操作が必要
  - 必要な操作内容:
  - 対象リソース:
  - 想定コマンド:
  ```

- ファイル名は内容が分かる英語スラッグにする（例: `issue-34-cloudfront-cache.md`）。

## テンプレート

```markdown
# <タイトル>

🔴 未対応（要対応）

- 種別: AWS操作
- 関連: #<issue番号> / PR #<PR番号>

## 症状

...

## 推定原因

...

## 切り分け手順

1. ...

## 要人間対応事項

⚠️ 要人間対応: AWS操作が必要
- 必要な操作内容:
- 対象リソース:
- 想定コマンド:
```

## 運用フロー

1. issue の解決に人間対応が必要と判明したら、上記テンプレートでファイルを作成する。
2. クライアントサイドで前進できた分は**それでも PR を出し**、その PR 本文からこのファイルを参照する。
3. このファイルを下の一覧に追記し、`docs/index.md` の索引も同じ PR で更新する。
4. 人間が対応を完了したら、ファイルを削除（または確定ドキュメントへ移行）し、一覧と `docs/index.md` を更新する。

> 補足: この仕組みは、既に「人間対応待ち」で棚上げ済みの事項を可視化するため、同じ未対応 issue を毎回ゼロから調査し直す無駄を減らすフックにもなります。着手前にこのディレクトリを確認すれば、対応済み・保留中の状況を把握できます。
