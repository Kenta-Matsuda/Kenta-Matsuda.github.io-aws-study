- 関連: #109
- 補足: 本ファイルに記載する構成・コマンドは、**サーバ / インフラ権限を持つ人間が検討・実行するための設計提案**です。エージェントは AWS 操作（`aws` / `sam` / `cdk` / `terraform` など）やバックエンド / MCP 接続のデプロイを一切実行していません。本 issue の成果物はこの設計ドキュメントです。

## 症状

issue #109 のフィードバックは、模擬問題生成の**信頼性**を高めるための次の 2 点の提案と、1 点の懸念です。

1. **AWS ドキュメント MCP サーバによる grounding**: 公式の一次情報（AWS 公式ドキュメント）に基づいて問題を生成できると信頼性が増すのではないか。documentation 系の AWS MCP サーバを使う想定。
2. **LLM as a judge による検証**: 生成した問題の内容が正しいかを、別の LLM 呼び出しで審査（judge）する仕組みがあるとよい。
3. **懸念（トレードオフ）**: LLM の呼び出しが増えると Gemini のリクエスト上限に引っかかるのではないか。

現状のコードベースでは、上記のうち「MCP サーバ経由の一次情報 grounding」と「独立した LLM as a judge パイプライン」を**そのままの形では実装できません**。理由は「推定原因」に記載するアーキテクチャ上の制約です。

### 現在のベースライン（既に実装済みの grounding）

重要な前提として、**本アプリは既に「プロンプトレベルの grounding」を行っています**。「grounding が全く無い」わけではありません。

- `js/quiz.js` の `buildQuizSystemPrompt()`（および `buildSpeedQuizSystemPrompt()` / モック用プロンプト）は、システムプロンプトで AI に対し次を明示的に指示しています。
  - 「AWS 公式ドキュメントに記載がある内容のみに基づいて出題する」
  - 「存在しないサービスや機能を問題に含めない」
  - 「解説には根拠となる AWS 公式ドキュメントの URL を 1 件以上含める（形式: `参考: https://docs.aws.amazon.com/...`）」
- 生成された `explanation`（`参考:` URL を含む）は `js/ui.js` で Markdown としてレンダリングされ、ユーザーに提示されます（`els.quizExplanation`）。
- LLM 呼び出しは `js/gemini.js` の `callGemini()` がクライアントから直接 `https://generativelanguage.googleapis.com/.../generateContent` を叩く形で、`systemInstruction` にシステムプロンプトを渡します（`js/openai.js` にも同等の呼び出し経路があります）。失敗時は最大 3 回までのリトライを行います。

したがって #109 の提案は、**この既存のプロンプトレベル grounding を、MCP 経由の一次情報 grounding と judge 検証へ拡張する**ものと整理できます。ゼロからの導入ではなく、信頼性の底上げです。

## 推定原因

これは不具合ではなく、**アーキテクチャ上の制約**に起因します。

- 本サイトは **ビルドステップの無い静的 PWA（Vanilla JS + HTML）** で、**GitHub Pages** から配信される純粋なフロントエンドです。**バックエンド（サーバ / API / 常駐プロセス）が存在しません。**
- **MCP サーバ自体は自前でホストしなくてよい（メンテナ指摘の反映）。** AWS は公式のリモート MCP エンドポイント（マネージド提供）を出しているため、documentation / knowledge 系の一次情報 grounding は、**利用者が MCP サーバを常駐ホスティングせずに、公式のリモート MCP へ接続して**利用できます。従来この節に書いていた「MCP サーバを自前で常駐ホストする必要がある」という前提は誤りであり、ここで訂正します。ただし、**リモート MCP への接続にも認証情報とエンドポイント設定が必要**であり、その秘匿情報はブラウザだけで動く静的サイトには置けません。
- **したがって残る制約は「MCP サーバのホスティング」ではなく「呼び出しの仲介（バックエンドプロキシ）」です。** リモート MCP への問い合わせ・生成 LLM 呼び出し・judge 呼び出しを束ね、認証情報を隔離し、レート制御・キャッシュを行うサーバ側の仲介は、静的サイトの外に依然として必要になります（理由は下記のレート上限と秘匿情報の制約）。
- **LLM as a judge は「生成」に加えて「審査」の LLM 呼び出しを追加**します。現状はクライアントがユーザー自身の API キーで Gemini を直接呼ぶ設計のため、judge 呼び出しを足すと 1 問あたりの呼び出し回数が増え、**#109 が懸念するとおり Gemini のリクエスト上限（レート / クォータ）に近づきます**。呼び出しの集約・制御を行うには、レート制御やキャッシュを担うサーバ側の仲介（プロキシ）が実質的に必要になります。
- リモート MCP への grounding クエリや judge 呼び出しに使う認証情報（AWS 資格情報 / リモート MCP の接続キー・API キー等）を**クライアントに置くことはできません**（静的サイトのソースは全て公開されるため漏洩する）。秘匿情報を扱う処理はサーバ側に置く必要があります。

以上より、#109 の本質部分（リモート MCP 経由の一次情報 grounding、独立した judge パイプライン、レート制御プロキシ）は、**静的サイトには無いサーバ側の仲介（バックエンドプロキシ）を前提とする要人間対応事項**です。一方で **MCP サーバの自前ホスティングは、AWS 公式リモート MCP を使えば不要**であり、人間の負担はその分軽くなります。

## 切り分け手順

要人間対応と判断するに至った確認手順は次のとおりです。

1. **現在の grounding 実装を確認する。** `js/quiz.js` の `buildQuizSystemPrompt()` / `buildSpeedQuizSystemPrompt()` を確認し、AWS 公式ドキュメント準拠と参考 URL 添付の指示（プロンプトレベル grounding）が既に存在することを確認した。
2. **LLM 呼び出し経路を確認する。** `js/gemini.js` の `callGemini()`（`systemInstruction` にシステムプロンプトを渡し、クライアントから `generateContent` を直接呼ぶ / 最大 3 回リトライ）および `js/openai.js` の同等経路を確認し、呼び出しがブラウザから直接行われ、集約・レート制御を担うサーバが無いことを確認した。
3. **バックエンド / 仲介プロセスの有無を確認する。** リポジトリ内に API サーバ / サーバレス関数などの呼び出し仲介の定義が無いこと、`js/` が全てブラウザで動くクライアントモジュールであることを確認した。なお grounding 源としては、AWS 公式のリモート MCP（マネージド提供）を利用すれば MCP サーバの自前ホスティングは不要であり、必要なのは接続設定と仲介側であると整理した。
4. **配信形態を確認する。** GitHub Pages 配信の静的サイトであり、生成 / judge / リモート MCP への接続を束ねる仲介（バックエンドプロキシ）を実行する環境が無いことを確認した。
5. **懸念（レート上限）との突き合わせ。** judge を足すと 1 問あたりの LLM 呼び出しが増え、#109 が懸念する Gemini リクエスト上限に近づくため、呼び出しの集約・制御にサーバ側仲介が必要と結論づけた。

上記より、クライアントサイドで前進できる成果物は「MCP / judge パイプラインの実装ではなく、この構造化された設計・引き継ぎドキュメント」と「純粋にクライアントのみで前進できる小さな改善案の切り出し」であると判断した。

## 今すぐクライアントのみで前進できること（要人間対応ではない）

サーバ / MCP を導入しなくても、既存のプロンプトレベル grounding を強化する形で、**LLM 呼び出し回数を増やさずに**信頼性の体感を高められる余地があります（別 issue / PR として小さく実装可能）。

- **既存プロンプト grounding の強化**: `buildQuizSystemPrompt()` の信頼性ルールをより厳格化する（例: 参考 URL は `https://docs.aws.amazon.com/` ドメインに限定するよう明示、推測での出題を禁止する文言の強化）。追加の LLM 呼び出しは不要。
- **引用元 URL の可視化**: 解説内の `参考:` URL を、解説本文に埋もれさせず**独立した「出典」リンク**として UI に目立たせて表示する（`js/ui.js` の explanation 表示部）。ユーザーが一次情報へ辿りやすくなり、信頼性の検証をユーザー自身が行える。追加の LLM 呼び出しは不要。
- **軽量な自己チェック（任意・呼び出し増に注意）**: 生成と同一レスポンス内で「参考 URL が `docs.aws.amazon.com` を含むか」等をクライアント側で**形式的に検証**し、欠けていれば軽い注意表示を出す。これは追加の LLM 呼び出しを伴わないクライアント側バリデーションに留める（別 LLM による内容審査＝judge は下記の要人間対応側）。

上記は「信頼性向上の第一歩」であり、MCP 経由の一次情報 grounding や独立した judge の代替にはなりません。本質的な #109 の要望は下記の要人間対応事項が前提です。

## 要人間対応事項

リモート MCP 経由 grounding と LLM as a judge を実現するには、静的サイトの外に**呼び出しを仲介するサーバ側（バックエンドプロキシ）**を用意する必要があります。**MCP サーバ自体の自前ホスティングは、AWS 公式リモート MCP を使えば不要です。** 以下はサーバ / インフラ権限を持つ人間が検討・実行するための**設計案と想定構成**です（エージェントは実行しません）。

### 私（人間）が何をすればいいか（アクション手順）

メンテナからの「私が何をしたらいいか教えて」に直接答えるための、順序立てた具体手順です。**今すぐコード変更なしで着手できる最小ステップ**と、**バックエンドが必要な本格対応**を分けています。迷ったら上から順に進めてください。

#### まず着手できる最小ステップ（コード変更・AWS 課金なしで進められる）

1. **AWS 公式リモート MCP の確認**: AWS 公式のリモート MCP（documentation / knowledge 系）の**提供状況・エンドポイント・接続認証要件**を公式ドキュメントで確認する。ここで「自前で MCP サーバを立てる必要が無い」ことと、接続に必要な認証方式（キー / 署名など）を把握する。
2. **レート上限対策の方針決め**: Gemini のリクエスト上限対策（事前生成・問題プール・judge のサンプリング・バッチ生成・モデル使い分け）のうち、**まず採用するものを決める**。例えば「judge は全問ではなくサンプリング」「問題は事前生成してプール配信」など。コードもインフラも不要な意思決定ステップ。
3. **クライアント側だけで先に出せる改善の切り出し**: 上の「今すぐクライアントのみで前進できること」（既存プロンプト grounding の強化、出典 URL の可視化、形式的な自己チェック）を別 issue / PR として起票する。これは追加 LLM 呼び出し不要で、リモート MCP やバックエンドが整う前に信頼性の体感を上げられる。

#### バックエンドが必要な本格対応（AWS 権限・構築作業が必要）

4. **バックエンドプロキシの用意**: LLM API キー等の秘匿情報をクライアントに置かないための**最小のバックエンドプロキシ**（例: Lambda + API Gateway、CORS を GitHub Pages のオリジンに限定）を用意する。ここで **リモート MCP へ問い合わせて公式一次情報を取得 → 生成 LLM → judge** を束ねる。秘匿情報（LLM API キー / リモート MCP 接続情報）はここで隔離する。
5. **judge パイプラインとレート対策の実装**: 手順 2 で決めた方針に沿って、judge（合否基準・不合格時の再生成/破棄・ログ化）とレート上限対策（プール / キャッシュ / バッチ / モデル使い分け）をプロキシ側に組み込む。
6. **クライアント改修の起票**: 上記が用意できたら、クライアント（`js/quiz.js` / `js/gemini.js` / `js/ui.js` ほか）を「プロキシ経由生成」「出典 URL 可視化」「judge 済み表示」へ改修する作業を**別 issue / PR** として起票する。

> ポイント: 手順 1〜3 は今日からコード変更なしで進められます。手順 4〜6 は AWS 権限を持つ人間の作業（⚠️ 要人間対応）です。**MCP サーバの自前ホスティングは、公式リモート MCP を使う前提のため手順に含めていません。**

### アーキテクチャ設計案（概要）

1. **バックエンドプロキシ（必須）**: クライアントからの問題生成リクエストを受け、LLM 呼び出し・リモート MCP 呼び出し・judge をサーバ側で束ねる仲介。API キー / リモート MCP 接続情報等の秘匿情報をサーバ側に隔離し、**レート制御・キャッシュ・リトライ**を集中管理する。GitHub Pages のオリジンに CORS を限定する。
2. **AWS 公式リモート MCP（grounding 源 / 自前ホスト不要）**: **AWS 公式のリモート MCP エンドポイント（マネージド提供）** に接続し、問題生成前に該当トピックの**公式一次情報を取得**して生成プロンプトの根拠として与える（retrieval-augmented generation 的な grounding）。documentation / knowledge 系のリモート MCP を想定。**利用者側で MCP サーバをデプロイ・常駐ホストする必要はない**が、接続にはエンドポイント設定と認証が要る（正確な提供形態・名称・接続要件は AWS 公式ドキュメントで要確認）。接続は上記バックエンドプロキシから行い、認証情報はクライアントに置かない。
   - （従）**自前ホストの代替**: リモート MCP を使わず自前で MCP サーバを常駐ホストする選択肢も理論上は残るが、公式リモート MCP が使える限り不要であり、本ドキュメントはリモート利用を主とする。
3. **生成 LLM**: MCP から得た一次情報を根拠に問題（question/choices/correct/explanation + 参考 URL）を生成する。
4. **LLM as a judge（検証）**: 生成された問題を、別プロンプト（または別モデル）で「公式情報と矛盾しないか」「正解が妥当か」「参考 URL が実在・適合するか」の観点で審査し、不合格なら再生成 / 破棄する。judge 結果はサーバ側でログ化して品質改善に使う。
5. **レート上限対策（#109 の懸念への対応）**: judge 追加で呼び出しが増えるため、次を組み合わせて Gemini リクエスト上限を回避する。
   - **サーバ側キャッシュ / 事前生成**: 生成・検証済みの問題をプールに貯め、実行時はプールから配信して都度の LLM 呼び出しを減らす。
   - **judge のサンプリング**: 全問ではなく一定割合のみ judge にかける、または信頼度が低い生成のみ judge する。
   - **バッチ / オフライン生成**: ユーザーのリアルタイム操作から切り離し、バッチで生成・検証してからストアに格納する（`js/geminiBatch.js` 相当の考え方をサーバ側へ）。
   - **モデル / プロバイダの使い分け**: 生成と judge で上限やコストの異なるモデルを割り当て、単一クォータへの集中を避ける。

### 候補コンポーネント / リソース

上記設計を構築する場合の候補（いずれも人間が構成を検討・決定するもの）:

- **AWS 公式リモート MCP への接続（自前ホスト不要）**: documentation / knowledge 系の **AWS 公式リモート MCP エンドポイント**（マネージド提供）への接続設定・認証。MCP サーバの実行環境を自前で用意する必要はない（正確な名称・エンドポイント・接続要件は公式ドキュメントで要確認）。
- **バックエンドプロキシ / API（必須）**: 生成・grounding（リモート MCP 問い合わせ）・judge を束ねる HTTP API（サーバレス関数 + API Gateway 等）。CORS を GitHub Pages オリジンに限定。秘匿情報（LLM API キー / リモート MCP 接続情報）はここで隔離する。
- **問題プール / キャッシュストア**: 生成・検証済み問題や grounding 結果を保持する永続 / キャッシュ層（データベースまたはオブジェクトストレージ + キャッシュ）。
- **シークレット管理**: LLM API キー・MCP 接続情報を安全に保持する仕組み（シークレットマネージャ / 環境変数）。クライアントには一切置かない。
- **クライアント改修（別 issue）**: 生成をプロキシ経由に切り替え、出典（参考 URL）の可視化と judge 済みバッジ表示などを追加する `js/` 側の改修。
