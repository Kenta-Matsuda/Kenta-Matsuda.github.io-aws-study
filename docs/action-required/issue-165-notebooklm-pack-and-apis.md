# NotebookLM 向け学習パックと学習分析 API（保存 / 他 SaaS 連携）

🔴 未対応（要対応）

- 種別: 要人間対応（バックエンド / 検索基盤 / API 提供）。一部要素はクライアント側で個別提供可能。
- 関連: #165 / PR #180（関連 #117 #167）

## 症状

issue #165 のフィードバック（PR #180 の 2026-09-06 追加コメント）で、学習ライフ全体での使いやすさとして
次の 4 点の要望をいただいた。

1. 問題データの CSV ダウンロード（過去問復習のため。localStorage に保存済みのはず）
2. NotebookLM 向けの「学習パック」提供（試験ドメイン別の一次ソース一覧 / 重要ホワイトペーパーのリンク集 /
   問題集 CSV / 学習ルート Markdown / 用語集 CSV を ZIP にまとめ、NotebookLM ユーザーが一瞬で自分専用の
   RAG 環境を作れるようにする）
3. 一次リソース検索 API
4. 学習者の得意・不得意分析 API

このうち **1（CSV ダウンロード）は PR #180 でクライアントサイド実装済み**（`js/quizCsv.js` + 学習履歴モーダルの
「CSV で書き出し」ボタン）。本ドキュメントは残る **2〜4** を要人間対応として整理する。

## 推定原因（なぜクライアントだけでは完結しないか）

- **一次リソース検索 API（3）**: 全試験・全ドメインの一次ソースを横断検索するには、収集済み URL の
  インデックス（全文 / メタデータ）と検索エンドポイントが要る。静的サイトの JS だけでも `js/data/*.js` の
  リソース URL を対象にした簡易な**クライアント内検索**は作れるが、「API」として外部（NotebookLM 等）へ
  提供するには公開エンドポイントとサーバ側のインデックスが必要になる。
- **得意・不得意分析 API（4）**: 分析自体はクライアントで既に可能（`getQuizAnalytics()` がドメイン別の
  正答率を出している）。だがこれを **API として外部へ提供**するには、ユーザー横断のデータ保持と認証・
  公開エンドポイントが要る（issue #167 のフィードバック集約 DynamoDB と設計軸が重なる）。
- **NotebookLM 学習パック（2）**: 構成要素の多くは静的資産（リンク集・学習ルート Markdown・用語集）で、
  問題集 CSV は 1 で実装済み。ZIP 化もクライアントで可能。ただし「常に最新の一次ソースを反映し続ける」
  「ユーザーの学習状況に応じてパック内容を出し分ける」まで含めると、収集・更新パイプラインと（4 と同様の）
  分析 API が必要になる。

## 切り分け手順

1. **クライアントで個別提供できる範囲を先に出す**（バックエンド不要）:
   - 問題集 CSV: PR #180 で対応済み。
   - 学習ルート Markdown / 用語集 CSV: `js/data/*.js`（学習ステップ）と用語データからクライアントで生成し、
     `Blob` ダウンロードできる。既存の `exportQuizHistory`（Markdown 書き出し）と同じ経路で追加可能。
   - 一次ソースのリンク集: `js/data/*.js` のリソース URL をドメイン別に列挙して Markdown / CSV 出力できる
     （`scripts/collect-resource-urls.mjs` が既に URL 収集ロジックを持つ）。
   - これらを 1 つの ZIP に束ねる「NotebookLM パック（クライアント生成版）」までは、外部依存なしで実装できる
     見込み（ZIP 生成は追加ライブラリ無しで実装するか、方針を別 issue で判断）。
2. **バックエンドが本質的に必要な範囲を分離する**: 「API 提供」（3・4 の外部公開エンドポイント）と、
   一次ソースの継続的な収集・インデックス更新。これらは #117 のバックエンド実装計画・#167 の分析基盤と
   統合して判断する。
3. 収集 URL の死活は `scripts/check-resource-links.mjs` で機械的に確認できる（外部ネットワークが使える環境で）。

## 要人間対応事項

⚠️ 要人間対応: AWS操作が必要
- 必要な操作内容:
  - 一次リソース検索 API と得意/不得意分析 API の**公開エンドポイント**（例: API Gateway + Lambda）の設計・構築の意思決定。
  - 検索インデックス（一次ソースの URL / メタデータ、必要なら本文）を保持するデータストア（例: DynamoDB / OpenSearch）の採否とコスト方針の判断。
  - 分析 API がユーザー横断データを扱う場合の**認証・データ保持方針**（#167 と共通の論点）。
- 対象リソース:
  - API Gateway（公開 API のエンドポイント）
  - Lambda（検索 / 分析ロジック）
  - DynamoDB もしくは OpenSearch Service（インデックス / 集計データ）
  - CloudFront / S3（学習パック ZIP を配布する場合の静的配信。任意）
- 想定コマンド:
  - 本リポジトリからは AWS 操作を実行しない（禁止事項）。必要なコマンド例は #117 の
    [バックエンド実装計画](issue-117-backend-implementation-plan.md) に集約済みのため、そちらの
    IaC / CLI 手順に合流させて判断すること。

## 次のアクション（クライアント側で先行できるもの）

- 学習ルート Markdown / 用語集 CSV / 一次ソースリンク集の**個別ダウンロード**を、問題集 CSV と同じ経路で
  追加する（バックエンド不要）。実装するかは利用実態とスコープを見て別 issue / PR で判断する。
- NotebookLM パック（クライアント生成 ZIP）は、上記の個別ダウンロードが揃ってから束ねる形にすると
  実装が段階的で安全。
