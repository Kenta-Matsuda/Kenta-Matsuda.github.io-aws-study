# ストリーク維持のためのプッシュ通知（アプリを閉じている間に届く通知）

🔴 未対応（要対応）

- 種別: 要人間対応（バックエンド / Web Push サービス）
- 関連: #107
- 補足: 本ファイルに記載する構成・コマンドは、**サーバ / 通知インフラを扱える人間が検討・実行するための提案**です。エージェントは AWS 操作（`aws` / `sam` / `cdk` / `terraform` など）を一切実行しません。

## 症状

issue #107 は Duolingo 風に「ユーザーへ沢山通知して学習継続を促す仕組み」を求めています。このうち、**アプリ（タブ）を閉じている間にも端末へ届く本物のプッシュ通知**は、現状のコードベースだけでは実装できません。

- ブラウザのタブを閉じた後や、後日の決まった時刻に「学習を続けて！」という通知を**能動的に配信**する経路が存在しない。
- 通知を送るには「誰に・いつ・何を送るか」を保持し、スケジュールに従って送信するサーバ側の仕組みが必要だが、それが無い。

> なお、**アプリを開いている間に表示するローカルなリマインド**（ストリークが途切れそうなときの通知 / アプリ内ナッジ）と、ストリークのマイルストーン祝福などの内発的動機づけ要素は、この PR でクライアントサイドのみで実装済みです（`docs/issues/streak-engagement.md` を参照）。本ファイルが扱うのは、それでは実現できない**サーバ依存のプッシュ通知**部分のみです。

## 推定原因

これは不具合ではなく、**アーキテクチャ上の制約**に起因します。

- このサイトは **ビルドステップの無い静的 PWA（Vanilla JS + HTML）** で、**GitHub Pages** から配信される純粋なフロントエンドです。
- **バックエンド（サーバ / API / データベース）が存在しません。** 学習状態は各ブラウザの `localStorage`（`js/storage.js`）にのみ保存されます。
- Web の「アプリを閉じていても届くプッシュ通知」は、**Push API + Service Worker + Web Push サービス**の組み合わせで成立します。具体的には次が必須です。
  - 各ブラウザで取得した **Push Subscription（購読情報）をサーバ側に保存**する。
  - **VAPID 鍵**（送信元を識別する公開鍵 / 秘密鍵）を用意し、秘密鍵を安全に保管する。
  - **決まったタイミングでプッシュを送信するサーバ / スケジューラ**（例: 「今日まだ学習していないユーザーへ夕方に送る」）を用意する。
- これらはいずれも**サーバ側コンポーネント**であり、クライアント単体（ブラウザ内のローカルデータのみ）では成立しません。

## 切り分け手順

要人間対応と判断するに至った確認手順は次のとおりです。

1. **既存の永続層 / 送信経路を確認する。** `js/storage.js` を確認し、状態が `localStorage` のみに保存され、外部への送信経路や購読情報の保存先が無いことを確認する。
2. **Service Worker の役割を確認する。** `sw.js` はアプリシェルのキャッシュ（オフライン表示）のためのもので、`push` イベントの受信ハンドラや購読処理を持たないことを確認する。
3. **バックエンド有無を確認する。** リポジトリ内に API サーバ / サーバレス関数 / データベース / スケジューラ / VAPID 鍵管理が存在しないことを確認する。
4. **機能要件との突き合わせ。** 「アプリを閉じている間に届くプッシュ通知」は購読情報の保存・VAPID 鍵・送信スケジューラを必須とするため、クライアントのみでは実装不能と結論づける。
5. **クライアントで前進できる範囲を確定する。** アプリを開いている間のローカル通知 / アプリ内ナッジ、ストリークのマイルストーン祝福はクライアントのみで実装可能と判断し、この PR で実装した。

上記より、サーバ依存のプッシュ通知については「実装ではなく、この構造化された設計・引き継ぎドキュメント」をクライアントサイドの成果物として残すと判断した。

## 要人間対応事項

アプリを閉じている間にも届くプッシュ通知を実現するには、静的サイトの外に通知インフラを用意する必要があります。以下はサーバ / AWS 権限を持つ人間が検討・実行するための**設計案と想定コマンド**です（エージェントは実行しません）。

### バックエンド設計案（概要）

- **VAPID 鍵の生成 / 保管**: Web Push の送信元を識別する公開鍵 / 秘密鍵を生成し、秘密鍵をシークレットとして安全に保管する。公開鍵はクライアントの購読時に使う。
- **Service Worker の拡張**: `sw.js` に `push` イベントハンドラ（`self.registration.showNotification(...)`）と `notificationclick` ハンドラを追加し、クライアントに `pushManager.subscribe({ applicationServerKey })` で購読させる。
- **購読情報（Push Subscription）の保存 API**: クライアントから受け取った購読情報とユーザー識別子・学習状態（最終学習日など）をサーバ側データストアに保存する Write API。
- **送信スケジューラ**: 「今日まだ学習していないユーザー」を定期的に抽出し、Web Push（VAPID 署名付き）で通知を送るバッチ / スケジュール実行。
- **クライアント改修**: 既存の opt-in リマインダー設定（`getStudyReminderEnabled` / `setStudyReminderEnabled`）を拡張し、有効化時に Push 購読を行い、購読情報を保存 API へ送る経路を追加する。バックエンド未接続時は現在のローカル通知 / アプリ内ナッジにフォールバックする。

### 候補 AWS リソース

上記設計を AWS で構築する場合の候補（いずれも人間が構成を検討・決定するもの）:

- **Amazon DynamoDB**: Push Subscription・ユーザーの最終学習日などを保持するテーブル。
- **AWS Lambda**: 購読保存 API と、プッシュ送信バッチの処理本体（Web Push ライブラリで VAPID 署名して送信）。
- **Amazon API Gateway**（HTTP API）: クライアントからの購読保存エンドポイントを公開。CORS を GitHub Pages のオリジンに限定。
- **Amazon EventBridge Scheduler**: 「毎日夕方に未学習ユーザーへ送信」などの定期実行トリガ。
- **AWS Secrets Manager / SSM Parameter Store**: VAPID 秘密鍵の安全な保管。

### ⚠️ 要人間対応: AWS操作が必要

- **必要な操作内容:**
  - VAPID 鍵ペアを生成し、秘密鍵をシークレットとして安全に保管する。
  - Push Subscription を保存するデータストアと保存 API を構築する。
  - 未学習ユーザーへ Web Push を送るスケジューラ / 送信バッチを構築する。
  - `sw.js` に `push` / `notificationclick` ハンドラを追加し、クライアントに購読処理と購読情報送信の経路を追加する改修を、別 issue / PR として起票する。
- **対象リソース:**
  - Amazon DynamoDB（購読情報 / 学習状態テーブル）
  - AWS Lambda（購読保存 API / プッシュ送信バッチ）
  - Amazon API Gateway（HTTP API エンドポイント）
  - Amazon EventBridge Scheduler（定期送信トリガ）
  - AWS Secrets Manager または SSM Parameter Store（VAPID 秘密鍵の保管）

  ```bash
  # ここに記載するコマンドはエージェントが実行するものではなく、
  # サーバ / AWS 権限を持つ人間が内容を精査・調整したうえで実行する「提案」です。
  ```
