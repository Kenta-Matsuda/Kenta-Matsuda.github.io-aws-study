## 症状

issue #225（フィードバックフォームからの要望の要約）:

> 模擬試験問題は**推奨リソースの内容を参考に**作るべき。ドメイン/タスクごとの出題数（試験構成）を決め、タスクごとに参照リソースを決め、その内容を読み込んで問題と解説を生成し、シャッフルして出題する。Professional は単元横断的な作り方が必要かも。シャッフルなどエージェント不要な部分はエージェントを使わない。

現状の AI 生成問題は、**推奨リソース（`js/data/*.js` の `resources[].items[].url`）の中身を一切参照していません**。

## 推定原因（＝現状の生成パイプラインの実態）

コードを監査した結果（2026-10-11 時点）:

| 工程 | 現状 | 場所 |
|---|---|---|
| 試験構成（ドメイン配分） | **実装済み**。ドメインの `weight` に比例して出題枠を割り当て（切り捨て + 最大剰余）、枠順を Fisher-Yates でシャッフル。※ タスク単位の配分は無く、タスクはモデルにランダム選択させている | `js/quiz.js` `assignDomainTargets` / `buildGeneralQuizUserPrompt` |
| 参照リソースの決定 | **無し**。プロンプトに渡るのはタスク ID・タイトル・タスクステートメント本文のみ | `js/ui.js` `buildTaskAiContext` |
| リソース内容の読み込み | **無し**。問題生成の呼び出しは `tools` を渡しておらず、Gemini `url_context` も未使用（AI チャットでは使用済み） | `js/ui.js` 事前生成ループ / `js/chat.js` |
| 問題・解説の生成 | 1 問ずつ生成。解説の出典 URL はモデルの記憶から書かれ、検証されない | `js/quiz.js` `buildMockQuizSystemPrompt` |
| シャッフル | ドメイン枠のみ。**選択肢はシャッフルしておらず**、正解記号の偏りはモデル任せ | `js/quiz.js` |
| 単元横断（Professional） | 無し。1 問 = 1 タスク前提 | — |

技術的制約（既存調査 `issue-138-ai-chat-exam-grounding.md` で実地検証済み）:

- `docs.aws.amazon.com` も AWS 公式リモート MCP も **CORS ヘッダを返さない**ため、ブラウザから直接本文を取得できない。
- **Gemini の `url_context` ツール**は Google 側でページを取得するため CORS の影響を受けず、本リポジトリの AI チャットで実績がある。ただし **Gemini プロバイダ限定**（OpenAI 経路では無視される）で、取得ページは入力トークンとして課金される。
- 自前プロキシ（Lambda + Function URL 等）を置けばプロバイダ非依存にできるが、AWS 操作と運用が必要（`issue-117-backend-implementation-plan.md`）。

## 切り分け手順（設計案：決定的処理と LLM 処理の分離）

issue の指摘どおり、**LLM が要らない工程はコードで決定的に行い、LLM は「読んで作る」工程だけに使う**。

```
[決定的] ① 試験構成  →  [決定的] ② 参照リソース選定  →  [LLM] ③ 読込+生成  →  [決定的] ④ 検証・シャッフル
                                                         ↑ Professional: ③' 横断シナリオ
```

1. **① 試験構成（コード・エージェント不要）**: 既存の `assignDomainTargets` を**タスク単位**に拡張する。ドメイン枠をそのドメイン内のタスクへ均等（またはタスクの `knowledge` 数比例）に配分し、どのタスクから何問出すかを生成前に確定させる。純関数としてテスト可能。
2. **② 参照リソース選定（コード・エージェント不要）**: タスクの `resources[].items[]` から `recommend` と種別（公式ドキュメント > ホワイトペーパー > ブログ）で優先度付けし、1 問あたり 1〜3 URL を決定的に選ぶ。ロケールに応じて `urlEn` を使う。問題ごとに異なる URL を回すことで出題の偏りも抑えられる。
3. **③ 読込 + 問題・解説生成（LLM）**: Gemini 経路では選んだ URL を `url_context` で読ませ、「**この資料に書かれている事実だけで**問題・正解・解説を作り、根拠にした URL を `sources` に返す」と指示する。OpenAI 経路や `url_context` 非対応モデルでは、従来どおりタスクステートメントのみでの生成にフォールバックする（AI チャットと同じリトライ方式）。
4. **③' Professional / 横断問題（LLM）**: 1 問に 2〜3 タスク（異なるドメインを含む）を割り当て、それぞれのリソースを渡して「複数要件を満たすシナリオ問題」を生成させる。① の段階で「横断枠」の比率（例: Professional は 50%）を決め、その枠にタスクの組み合わせを割り当てる。
5. **④ 検証・シャッフル（コード・エージェント不要）**: JSON 形式検証、**選択肢のシャッフルと `correct` の付け替え**（現状の正解記号の偏りも解消できる）、`sources` が ② で渡した URL の部分集合であるかの検査（渡していない URL の捏造を検出）、最後に問題順のシャッフル。

段階導入案（それぞれ独立した PR にできる）:

- **Step A（コストゼロ・すぐ着手可）**: ④ の選択肢シャッフルと ① のタスク単位配分。LLM 呼び出し回数もトークンも変わらない。
- **Step B（クライアントのみ）**: ② の決定的リソース選定と、選んだ URL・タイトル・`note` をプロンプトに**メタデータとして**渡す（本文は読ませない）。解説の出典を推奨リソースに寄せられ、`sources` 検査も可能になる。
- **Step C（Gemini 限定・トークン増）**: ③ で `url_context` による本文読み込み。
- **Step D**: ③' Professional 向け横断生成。
- **（将来）**: プロバイダ非依存にするなら自前プロキシで本文取得・キャッシュ、または事前生成した問題バンク（`offline-exam-bank.js` の拡張）を CI/エージェントで作る案。後者は利用者のトークン消費ゼロで、生成時に人手/LLM-judge 検証も挟める。

## 要人間対応事項

⚠️ 要人間対応: プロダクト判断が必要（現段階の Step A〜D では AWS 操作は不要）

- **決定 1 — 生成方式**: (a) 利用者の API キーでその場生成（Step C/D）、(b) 事前生成の問題バンクを配布（利用者コストゼロ・品質検証しやすいが更新はバッチ）、(c) 両方。
- **決定 2 — トークンコスト**: Step C は 1 問ごとに数ページ分の入力トークンが増える。65 問の模擬試験 1 回で利用者の無料枠/課金に与える影響を許容するか、上限（1 問あたり URL 数・ページ数）をどう置くか。
- **決定 3 — プロバイダ差の扱い**: `url_context` は Gemini 限定。OpenAI 利用者はフォールバック（現状同等）で良いか、自前プロキシ（AWS 操作要）まで行うか。
- **決定 4 — Professional の横断比率**: 横断シナリオ問題の比率と、組み合わせるタスク数。
- 推奨: まず **Step A → Step B** をエージェントに依頼（コスト・外部依存なし）、Step C 以降は決定 1〜3 の後。
