# AWS 公式ドキュメントが対応する全言語へのサイト対応（多言語化）

🔴 未対応（要対応）

- 種別: 要人間対応（プロダクト判断 / 翻訳ソース・品質基準の決定 / 翻訳コンテンツのオーナーシップ）
- 関連: #197
- 位置づけ: 本ファイルは**スコープ評価と人間側への引き継ぎ**です。エージェントは機械翻訳した試験コンテンツを一切コミットしていません（後述の理由による）。多言語化は技術実装だけでなく**翻訳の出典・品質保証・保守体制というプロダクト判断**を伴うため、その意思決定を明文化して残します。

## 症状

issue #197（フィードバックフォームからの要望）:

> AWSの公式ドキュメントが対応している言語はすべて、このサイトでも対応できるようにして。

現在このサイトの i18n は **日本語（`ja`）と英語（`en`）の 2 言語のみ**に対応しています。「AWS 公式ドキュメントが対応する全言語」（一般に 10 言語以上）への拡張は未対応です。

## 推定原因（＝現状の設計が 2 言語前提であること）

現在の i18n アーキテクチャを実際に監査した結果、多言語化には次の 4 レイヤーすべてに手を入れる必要があることが分かりました。単に「翻訳ファイルを 1 つ足す」だけでは完結しません。

### 1. i18n コアが 2 言語をハードコードしている（`js/i18n.js`）

- `SUPPORTED_LOCALES = ['ja', 'en']`、`DEFAULT_LOCALE = 'en'` がモジュール先頭で固定。
- `initI18n(localeData, urlMapping)` は `{ ja, en }` という **2 キー固定のオブジェクト**を受け取る前提（`t()` のフォールバックも `locales['en']` 固定）。
- ブラウザ言語検出は `browserLang === 'ja' ? 'ja' : DEFAULT_LOCALE` の**二分岐**で、`ja` 以外はすべて `en` に丸められる。
- `getLocalizedUrl(jaUrl, enUrl)` は `currentLocale === 'en'` のときだけ英語 URL / `urls.json` のマッピングを引く、**ja↔en 前提の 2 値ロジック**。

つまり新しい言語を足すには、`SUPPORTED_LOCALES` の拡張だけでなく、URL ローカライズと言語検出の**多言語一般化**が必要です。

### 2. ロケール辞書は ja/en の相互ミラー（`js/locales/ja.json` / `en.json` / `urls.json`）

- `ja.json` と `en.json` は**全キーが相互ミラー**（現在それぞれ 401 行）。新言語ごとに、この全キーを漏れなく訳した `<lang>.json` を用意する必要がある。
- `urls.json` は「日本語 URL → 英語 URL」の 1 対 1 マッピング（`/jp/` を含む URL を英語版に差し替える）。新言語では、その言語版の AWS ドキュメント URL が存在する範囲で対応表を作る必要があるが、**全 URL に各言語版が存在するとは限らない**（存在しない場合のフォールバック方針も要決定）。

### 3. 起動時ロード（`js/app.js`）と言語スイッチャー UI（`index.html` / `js/ui.js`）

- `js/app.js` の `loadLocales()` は `ja.json` / `en.json` / `urls.json` の **3 本を固定で `fetch`** し、`initI18n({ ja, en }, urls)` に渡す。新言語ごとに fetch 対象を増やす必要がある。
- 言語トグル（`langToggleBtn`）は `getLocale() === 'ja' ? 'en' : 'ja'` の**2 値トグル**。
- 設定モーダルのスイッチャー（`index.html` の `#langSwitch`）は `data-lang="ja"` / `data-lang="en"` の**2 ボタン固定**。3 言語目以降はボタン追加、あるいはセレクトボックス等への作り替えが必要。
- 追加ファイル（新しい locale JSON）は Service Worker のキャッシュ一覧（`sw.js`）にも追記が必要。

### 4.（最難関）試験コンテンツ本体が ja/en 埋め込み二言語で書かれている（`js/data/*.js`）

これが多言語化の**本質的な難所**です。i18n の仕組み（1〜3）を一般化しても、**表示すべき中身が無ければ意味がありません**。

- 試験データ（`js/data/aif-c01.js` など試験コード単位、十数ファイル）は、UI 文言のような「キー → 辞書引き」方式ではなく、**各項目に日本語フィールドと英語フィールドを並記**する方式です（例: `title` / `jpTitle`、`description` / `descriptionEn`、`label` / `labelEn`、`note` / `noteEn`、`url` / `urlEn` …）。
- したがって新言語の追加は、`<field>Xx` のような**言語別フィールドを全データファイル・全項目に足す**（またはデータ構造をロケール別に再設計する）作業になり、しかも中身は**人手 / AWS 公式ガイドで検証された正確な翻訳**でなければなりません。
- 試験ガイドの語彙・サービス名・出題範囲は正確性が命であり、**機械翻訳したものをそのままコミットすると誤訳・用語ゆれが試験対策情報として害になる**ため、エージェントはこれを行いません（下記トレードオフ参照）。

## 切り分け手順（多言語化を実際に進めるときの順序）

1. **対象言語の確定（要人間）**: 「AWS 公式ドキュメントが対応する言語」の正確な一覧を確定する。※ 本サンドボックスは外部ネットワーク非接続（INTEGRATIONS_ONLY）で AWS のサイトを参照できないため、**エージェントは言語一覧を断定していません**。人間が AWS 公式（AWS ドキュメント / 認定試験ページの言語切替）で現在対応している言語を確認して確定してください。
2. **i18n コアの一般化**: `js/i18n.js` の `SUPPORTED_LOCALES` を可変配列化し、`initI18n` を任意個数のロケール辞書を受け取れるようにする。言語検出・URL ローカライズを ja↔en 前提から多言語一般に拡張する。回帰は `tests/routing-lang.spec.mjs` を各言語へ拡張して担保する。
3. **辞書とローダの拡張**: 言語ごとの `<lang>.json`（全キー相互ミラー）と `urls.json` の多言語化、`js/app.js` のロード対象追加、`sw.js` キャッシュ追記。
4. **スイッチャー UI の作り替え**: 2 ボタン固定から、言語数に耐えるセレクト等へ（`index.html` の `#langSwitch` と `js/ui.js` の `wireSettingsModalSwitches` / `langToggleBtn` ハンドラ）。
5. **コンテンツ翻訳（最難関・要人間）**: `js/data/*.js` の全試験コンテンツを対象言語へ翻訳する。用語・サービス名は AWS 公式の各言語版に合わせる。翻訳の出典・品質基準・レビュー体制を先に決める（下記）。

段階導入の推奨: 1 言語ずつ「UI 文言のみ先行 → コンテンツは順次」ではなく、**UI とコンテンツが揃った言語だけを `SUPPORTED_LOCALES` に載せる**（半端に翻訳された言語を公開すると、キー欠落時に英語へフォールバックした混在表示になり、学習情報として品質を損なうため）。

## 要人間対応事項

この issue は AWS リソース操作（`aws` CLI など）を**必要としません**。代わりに、実装に先立って決める必要がある**プロダクト判断**が本質です。以下はエージェントが代行できない意思決定です。

⚠️ 要人間対応: プロダクト判断が必要（AWS 操作は不要）

- **決定 1 — 対象言語**: 「AWS 公式ドキュメントが対応する言語」を人間が公式サイトで確認して確定する（エージェントは外部参照不可のため一覧を断定していない）。全言語を一度に狙うか、需要の高い言語から段階導入するかも決める。
- **決定 2 — 翻訳の出典と品質基準**: 試験コンテンツ（`js/data/*.js`）の翻訳をどこから得るか（プロ翻訳 / コミュニティ / LLM + 人手レビュー）。用語・サービス名は AWS 公式の各言語版に合わせる、という品質バーを明文化する。**機械翻訳のみで未レビューのコンテンツは公開しない**方針を推奨。
- **決定 3 — コンテンツ翻訳の工数とオーナーシップ**: 十数試験ぶんの全項目（`title`/`description`/`knowledge`/`resources` の note まで）を対象言語ぶん翻訳・保守する体制と担当を決める。データ更新のたびに全言語を追従させる保守コストが継続的に発生する点を織り込む。
- **決定 4 — URL とフォールバック方針**: 各言語版 AWS ドキュメント URL が存在しない場合に、英語 URL / 日本語 URL のどちらへフォールバックするかを決める（`urls.json` の設計に影響）。

決定 1〜4 が固まれば、上記「切り分け手順」の 2〜4（i18n コアの一般化・辞書拡張・スイッチャー UI）は、**翻訳を推測せずに進められるクライアントサイド作業**としてエージェントが実装できます（コンテンツ翻訳そのものは決定 2・3 の体制に依存）。

## エージェント側で対応できる作業（プロダクト判断が決まったら）

- **[エージェント可]** `js/i18n.js` の `SUPPORTED_LOCALES` の可変化と `initI18n` の多言語対応、言語検出・URL ローカライズの一般化（翻訳の中身に依存しない機構部分）。
- **[エージェント可]** `js/app.js` のロケールロード拡張、`sw.js` キャッシュ追記、スイッチャー UI の多言語対応。
- **[エージェント可]** `tests/routing-lang.spec.mjs` を対象言語へ拡張した回帰テストの追加。
- **[エージェント可]** 各言語 `<lang>.json` の**キー骨組み（英語フォールバック付き空テンプレート）**の生成。※ ただし中身の翻訳は決定 2 の品質基準に従い人手検証が必要。
- **[エージェント不可]** 試験コンテンツの正確な翻訳そのもの（機械翻訳をコミットしない方針のため）。

## 次のアクション（人間）

1. 対象言語を AWS 公式で確認して確定する（決定 1）。
2. 翻訳の出典・品質基準・保守体制を決める（決定 2・3・4）。
3. 決定後、i18n 機構の一般化とスイッチャー UI の多言語対応（翻訳非依存の部分）をエージェントに依頼する。
