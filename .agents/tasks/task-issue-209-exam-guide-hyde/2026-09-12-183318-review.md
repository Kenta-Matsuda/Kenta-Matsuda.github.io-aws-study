# Exam-guide keyword catalog augmentation — v1-review fixes (#209) (v2)

The follow-up commit (`636c7ae`) responds to all five concerns from the v1 review. It adds three pure exported functions to `resourceSearch.js` — `isSafeCatalogSearchTerm` (drops over-matching short/unanchored catalog entries like bare `'Amazon Q'` from live search terms), `CONCEPT_SERVICE_ALIASES` + alias-expansion inside `augmentTermsWithCatalog` (bridges concept queries with no lexical overlap, e.g. `'BIツール'` → Amazon QuickSight), and `buildAugmentedScoringQuery` (scores grounding candidates against the augmented term set instead of the raw query). `ui.js` now tracks `augmentedTerms` in scope and feeds their joined form to `selectAiCandidates`. The spec is rewritten with two reversion-sensitive differential tests plus unit coverage for the new functions. The v1 no-op litmus finding for bare `'Quick'` is not "fixed" but honestly reframed in the docs as already-searchable/not-a-regression, with the real recall win moved to verbose and concept queries.

**Watch for:** the concept-alias gate uses `q.includes(conceptLower) || conceptLower.includes(q)`, and the reverse direction over-fires for short/generic single-token queries — a bare `'b'`, `'business'`, `'intel'`, or `'ビジネス'` query injects `Amazon QuickSight` (confirmed). Impact is bounded (QuickSight searches as `amazon AND quicksight`, adding only 2 real QuickSight docs, not a noise flood), so it is a mild precision wart, not a blocker. All five prior issues are otherwise genuinely resolved and verified against the real index.

**Verdict**: APPROVED

## High-level view

Every v1 concern was traced through the code and re-run against the real index, and each holds. The over-match guard filters exactly the two unanchored catalog entries (`'Amazon Q'` and `'3 層アーキテクチャ'`) while keeping `'Amazon Q Developer'`/`'Amazon Q Business'`; the differential tests both fail when `augmentTermsWithCatalog` is reverted to identity (baseline 0 for the verbose query, no QuickSight for `'BIツール'`) and pass with augmentation; grounding now scores against the augmented terms; and `selectAiCandidates`/`scoreResourceRelevance`/`searchResourcesMulti` bodies are untouched, so the wiring change is confined to the call site.

The docs are honest about what the mechanism does and does not do: bare `'Quick'` is explicitly documented as already-searchable rather than claimed as fixed, and the concept-alias table is disclosed as a small curated map, not a general semantic solution, with embedding-based semantic search called out as future scope.

The one new issue the follow-up introduces is the concept-alias substring gate firing in the reverse direction for short query tokens, pulling QuickSight into unrelated generic queries. Because the injected term is a full service name that AND-matches, the blast radius is small, but the gate direction is looser than intended.

### Over-match guard (v1 issue 3) — filters exactly the unanchored entries

`isSafeCatalogSearchTerm` strips punctuation per token (`/[^\p{L}\p{N}]/gu`), splits on whitespace, and rejects an entry only when it has a sub-2-char token AND ≤2 total tokens. Run against the real `buildExamKeywordCatalog()`, exactly two entries are filtered: `'Amazon Q'` (the intended target) and `'3 層アーキテクチャ'` (`3` + `層アーキテクチャ` → 2 tokens, one single-char). `'Amazon Q Developer'`, `'Amazon Q Business'`, `'Amazon QuickSight'`, `'AWS Glue'`, `'S3'`, `'EC2'`, `'PII / PHI'`, `'Amazon EMR'` all stay safe. The CJK regex retains Japanese characters via `\p{L}`/`\p{N}`, so `'層アーキテクチャ'` counts as a real anchor token; the incidental `'3 層アーキテクチャ'` drop is a weak search term either way, not a recall loss. `augmentTermsWithCatalog` no longer adds bare `'Amazon Q'`: for `['Amazon Q Developer とは']` the output contains `'Amazon Q Developer'` and not `'Amazon Q'`.

### Differential tests (v1 issue 2) — now reversion-sensitive

Both new end-to-end tests fail under an identity revert, which is the property the v1 test lacked:

```
verbose 'Amazon Q Developer とは'  baseline=0  augmented=9   (revert: augmented=0 → assert augmented>baseline fails)
concept 'BIツール'                  baseline QS=false  augmented QS=true  (revert: augmented QS=false → assert fails)
```

The verbose test compares augmented against `[query, ...expandedTerms]` (the pre-feature `ui.js` behavior) on the same index and asserts a non-empty delta; the concept test asserts QuickSight surfaces only with augmentation. Reverting `augmentTermsWithCatalog` to identity breaks both. The retained `'Quick'` unit test still passes but is no longer load-bearing for reversion detection.

### Concept alias (v1 issue 5) — works, but the gate direction is loose

The curated `CONCEPT_SERVICE_ALIASES` maps six concept strings to `Amazon QuickSight`, gated so only catalog-present services are added. `augmentTermsWithCatalog(['BIツール'], catalog)` yields `['BIツール', 'Amazon QuickSight']` and surfaces 2 QuickSight docs where the baseline surfaced 0.

The hit test is `q.includes(conceptLower) || conceptLower.includes(q)`. The forward direction (query contains the concept) is the intended semantics. The reverse direction (`conceptLower.includes(q)`) fires whenever a query token is a substring of a concept word, which over-fires for short/generic queries:

```
query 'business' -> QuickSight injected (business ⊂ 'business intelligence')
query 'b'        -> QuickSight injected
query 'intel'    -> QuickSight injected
query 'ビジネス'  -> QuickSight injected (⊂ 'ビジネスインテリジェンス')
```

A single-character `'b'` query pulling in QuickSight is clearly unintended. The saving grace is blast radius: the injected term is the full service name `Amazon QuickSight`, which searches as `amazon AND quicksight`, so `'business'` augmented adds only 2 real QuickSight documents (10 → 12), not the ~38-result flood the old bare-`'Amazon Q'` term produced. So this is a precision wart, not a grounding-dilution regression. Dropping the reverse direction (or requiring `q.length >= 2` / a minimum overlap) would tighten it without losing the intended `'BIツール'`/`'ダッシュボード'` cases, since those fire on the forward direction.

### Grounding scored on augmented terms (v1 issue 4)

`ui.js` passes `buildAugmentedScoringQuery(augmentedTerms)` to `selectAiCandidates` instead of the raw `query`. `augmentedTerms` is initialized to `[query]`, reassigned to the augmented set on the success path, and reset to `[query]` in the `catch`, so every path reaching the grounding step has a defined term set. `selectAiCandidates`, `scoreResourceRelevance`, and `searchResourcesMulti` bodies are unchanged (the only diff mentioning them is new JSDoc). A catalog-only hit that scored 0 against the raw query now scores against the service name the catalog pulled in, so the 40-candidate cap no longer evicts it — which is the point of the fix.
