# Exam-guide keyword catalog to augment HyDE query expansion (#209)

Issue #209 uses "can 'Quick' be searched" as a litmus test for AI search: "Quick" stands for newer services (Amazon QuickSight / Amazon Q) the LLM may not have been trained on, so whether they surface depends on the app supplying context rather than the model guessing. The change adds two pure functions in `resourceSearch.js` — `buildExamKeywordCatalog` (harvests `knowledge`/`knowledgeEn` strings from step- and task-level exam data into a deduped, model-independent keyword catalog) and `augmentTermsWithCatalog` (unions the HyDE expanded terms with catalog entries that bidirectionally substring-match any query term). `ui.js` memoizes the catalog and folds it into the term list before `searchResourcesMulti`. The functions themselves are well-built and consistent with the existing HyDE code; the problem is that the mechanism does not actually move the needle on the issue's own litmus test.

**Watch for:** the "end-to-end" litmus test is not reversion-sensitive — it passes with augmentation fully removed (confirmed); and for the exact `'Quick'` query the augmentation yields zero additional resources because `searchResources` already substring-matches `'Quick'` into `'QuickSight'` (confirmed). Separately, the catalog injects the term `'Amazon Q'`, which searches as `amazon AND q` and matches ~38 unrelated resources, adding grounding noise (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The augmentation only fires when a query term lexically overlaps a catalog service name (either direction of substring match). That is exactly the situation where the existing case-insensitive substring search in `searchResources` already finds the resource, so for the `'Quick'` litmus query the catalog adds the term `'Amazon QuickSight'` but zero new resources — and since AI grounding is derived from those same search results, the model sees nothing new either. Where the change genuinely helps is verbose/multi-token queries: `'Amazon Q Developer とは'` returns 0 raw results (searched as one AND-phrase) but 38 once the catalog contributes the clean `'Amazon Q'` / `'Amazon Q Developer'` tokens. It does not help a truly vague query with no lexical overlap (e.g. `'BIツール'` → still 0), which is the harder half of the issue.

The new spec's "end-to-end" test is the main quality gap: it asserts QuickSight surfaces for `['Quick', 'Amazon Athena']`, but that holds whether or not augmentation runs, so it guards nothing about the new behavior and gives false confidence. The unit tests for both pure functions are otherwise thorough and correct.

The catalog contributes the bare token `'Amazon Q'`. Because search splits on whitespace and substring-matches, `amazon AND q` matches queue/quotas/parquet and similar, so any query that pulls `'Amazon Q'` into the term list widens grounding with noise. Grounding relevance is scored against the raw query, so catalog-only hits (a QuickSight doc pulled via `'Amazon QuickSight'` for a query that doesn't contain "quick") score 0 and risk being dropped past the 40-candidate cap.

The pure-function design, defensive input handling, dedup/ordering semantics, and JSDoc match the surrounding code well; the concern is efficacy and test rigor, not code quality.

### Why the augmentation is a no-op for the `'Quick'` litmus test

`searchResources` lowercases every record's title/note/url into a haystack and requires each whitespace-split query token to be a substring (`haystack.includes(term)`). `'Quick'` is a single token and is a substring of `'quicksight'`, so the raw query already hits every QuickSight document:

```
searchResources(index, 'Quick')                        -> 6 results
augmentTermsWithCatalog(['Quick'], catalog)            -> ['Quick', 'Amazon QuickSight']
searchResourcesMulti(index, ['Quick'])                 -> 6 results
searchResourcesMulti(index, ['Quick','Amazon QuickSight']) -> 6 results   (extra: 0)
```

The catalog adds the string `'Amazon QuickSight'` to the term list, but that term finds a subset of what `'Quick'` already found, so the union is unchanged. Grounding candidates come from this same result set, so the model's candidate list is identical with and without the change. For the issue's stated litmus query, the change is inert (confirmed by direct module execution).

The augmentation's guard condition — a query term is a substring of a catalog entry, or vice versa — is structurally the same predicate the substring search already applies at the resource level. So whenever augmentation *can* fire on a term, plain search on that term already matched the corresponding resource titles. The two mechanisms overlap instead of complementing.

### Where it does help, and where it still doesn't

Multi-token queries expose a real gap in the AND-based search that the catalog repairs:

```
searchResourcesMulti(index, ['Amazon Q Developer とは'])                     -> 0
augmentTermsWithCatalog(['Amazon Q Developer とは'], catalog)                -> [..., 'Amazon Q', 'Amazon Q Developer']
searchResourcesMulti(index, augmented)                                       -> 38   (extra: 38)
```

Here the raw query is one term whose tokens (`amazon`, `q`, `developer`, `とは`) must all co-occur in a single document, which nothing satisfies; the catalog contributes the clean service tokens and recovers results. This is a genuine improvement for verbose natural-language queries.

But the harder half of #209 — a vague query that names an *intent* rather than the service — gets nothing, because the relevance predicate is lexical:

```
augmentTermsWithCatalog(['BIツール'], catalog)   -> ['BIツール']   (no catalog entry added)
```

`'BIツール'` neither contains nor is contained by `'Amazon QuickSight'`, so no catalog entry is pulled and QuickSight never surfaces. The issue's framing ("pre-organize which services/concepts matter per exam guide, use that to inform expansion") implies an association from concept to service that survives when the words don't overlap; substring matching does not provide that.

### The end-to-end test guards nothing

```js
const expandedTerms = ['Amazon Athena'];
const terms = augmentTermsWithCatalog(['Quick', ...expandedTerms], catalog);
const results = searchResourcesMulti(index, terms);
expect(hasQuickSight).toBe(true);
```

Reverting the augmentation (using `['Quick', 'Amazon Athena']` directly, as `ui.js` did before this change) produces the same result:

```
WITH augmentation      -> hasQuickSight: true   terms: ['Quick','Amazon Athena','Amazon QuickSight']
REVERTED (no augment)  -> hasQuickSight: true   terms: ['Quick','Amazon Athena']
```

The assertion is satisfied by the raw `'Quick'` substring hit, so it cannot fail if the feature is removed. A test that claims to verify "the model omits QuickSight yet it still surfaces" should isolate the augmentation's contribution — for example, assert that a query with no substring overlap surfaces the service only after augmentation, or diff the augmented result set against the un-augmented one on the same index and assert the delta is non-empty.

### `'Amazon Q'` as a search term widens grounding with noise

The catalog legitimately contains `'Amazon Q'`, `'Amazon Q Developer'`, `'Amazon Q Business'`. When `'Amazon Q'` enters the term list it is searched as two tokens under AND:

```
searchResources(index, 'Amazon Q')  -> 38 results
```

Those 38 include queue/quotas/parquet/data-quality documents where `q` is an incidental substring, not Amazon Q resources. Feeding them as grounding dilutes the candidate pool the model ranks over. Single-letter and other ambiguous trailing tokens should be guarded — require a minimum token length, apply word-boundary matching for short service names, or skip catalog entries whose tokens are too generic — before they are added as live search terms.

### Grounding relevance is scored on the raw query, not the augmented terms

`ui.js` calls `selectAiCandidates(candidates, query, 40)` with the original `query`. `scoreResourceRelevance` splits that raw query and scores title/url/other hits. A resource that entered the candidate list *only* because a catalog term matched it (e.g. a QuickSight doc pulled by `'Amazon QuickSight'` for a query that does not itself contain "quick") scores 0 against the raw query and sorts to the bottom, so it can be evicted by the 40-candidate cap before the model ever sees it. The augmentation can therefore add a resource to the visible card list yet fail to get it into grounding. Scoring against the augmented term set (or explicitly protecting catalog-sourced hits) would make the pulled-in service actually reach the model — which is the point of the feature.

### Pure-function design and quality

Independent of efficacy, the two functions match the surrounding conventions: `buildExamKeywordCatalog` walks the same step→domain→task topology as `buildResourceIndex` and reuses the shared `str()` helper; `augmentTermsWithCatalog` mirrors the dedup/ordering/`Number.isFinite(limit)` patterns already in the file; and the memoization in `ui.js` follows the existing `getResourceSearchIndex()` shape. The unit tests for both functions are thorough (both-level collection, trim/empty, case-insensitive dedup, bare-string input, null tolerance, order, limit, non-mutation, substring both directions). Only the "end-to-end" test is deficient — see above.
